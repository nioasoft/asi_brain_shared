2. Security audit runbook (the 30-min playbook)

Four steps. Apply to any Next.js / Node.js project before shipping to a client. The whole thing takes about 30 minutes once you know the moves.

2.1 Step 1 — Dependency vulnerabilities (npm audit)

Goal: Catch known CVEs in installed packages.

# In the project root:
npm audit --omit=dev          # production deps only
npm audit                     # everything
npm outdated                  # what's old

How to read the output

  • Critical / High Must fix before shipping. Try npm audit fix first; if that fails, manually upgrade the package.
  • Moderate Fix if exploitable in your usage path (look at the CWE description).
  • Low / Informational Can ignore if the vulnerable code path is not reachable.

Common gotchas

  • npm audit fix --force can break the app — run tests after. Prefer manual upgrade for major-version bumps.
  • If lockfile is pnpm-lock.yaml or yarn.lock, use pnpm audit / yarn audit instead.
  • Next.js projects: pay extra attention to next itself, @auth/*, anything that touches server actions.

2.2 Step 2 — Auth boundary tests (IDOR — "listed from users")

Goal: Verify that User A cannot read or modify User B's data by tweaking IDs in URLs or API bodies.

This is the single highest-value test because IDOR (Insecure Direct Object Reference) is the most common and most damaging bug in CRUD apps. Having a login page is not the same as having authorization.

Manual test (~10 min per app)

  1. Create two test users: alice@test.com and bob@test.com.
  2. Log in as Alice. Create a resource (a record, an order, a profile, whatever the app owns). Note its ID — e.g., /api/orders/42.
  3. Open Network tab in browser dev tools. Find the API call to fetch order 42. Note its URL.
  4. In another browser / incognito, log in as Bob.
  5. From Bob's session, directly request Alice's resource:
    • URL approach: paste https://app.example.com/orders/42 in Bob's browser.
    • API approach: in Bob's dev console, run fetch('/api/orders/42').then(r => r.json()).then(console.log)
  6. PASS Bob gets 403 Forbidden or 404 Not Found.
    FAIL Bob sees Alice's data.

Automated grep (find suspicious code patterns)

# Find API routes that fetch by ID but don't filter by ownership
grep -rn "findUnique\|findFirst\|findOne" --include="*.ts" --include="*.js" -A 3 . \
  | grep -i "where.*id" \
  | grep -v "userId\|user_id\|ownerId\|owner_id"

Any match that doesn't filter by userId/ownerId is suspicious — it returns the record regardless of who's asking.

Common Next.js / API-route patterns

PatternVerdict
prisma.order.findUnique({ where: { id } })FAIL unless followed by an ownership check.
prisma.order.findUnique({ where: { id, userId: session.user.id } })PASS
Server actions / route handlers that take params.id from the URL and look it up without filtering by sessionFAIL
Don't forget mutation endpoints. Also test:
  • PATCH /api/orders/42 from Bob's session with a body change — does it succeed? If yes, FAIL.
  • DELETE /api/orders/42 from Bob's session — does it succeed? If yes, FAIL.

Fix pattern: every database read/write inside a route should be scoped by the current user's session — never trust an ID from the URL or body on its own.

2.2b Step 2b — Supabase RLS (Row-Level Security) deep dive (IG reel DYxb9K-RC7n · 2026-05-26)

If the project uses Supabase (or any Postgres-backed Next.js stack), IDOR has a database-level fix that's even more important than the route-level check above: Row-Level Security policies. The reel framed it sharply: "Most of you have Supabase tables that are publicly readable, whether you know it or not — not because you chose it, because that's the default for AI-produced apps."

Why this matters more than route-level checks: if a developer (or Claude) ever forgets the ownership check on a single route, the route is wide open. RLS is enforced by Postgres itself — every query is filtered at the database, so even a buggy route can't leak data. Defense in depth. Always do both.

What to check right now (5 minutes)

  1. Open Supabase dashboard → Authentication → Policies.
  2. For every table that stores user data, you should see at least one policy per operation type (SELECT, INSERT, UPDATE, DELETE).
  3. Empty policies list = wide open. If RLS is enabled but no policies exist, the table denies everything — that's safe. If RLS is disabled, anyone with a valid session token can query the whole table.
  4. Check the toggle in the table editor: "Enable Row Level Security" must be ON for every table touching user data.

The minimum required policies

Table typePolicies needed
Stores user-specific data (orders, profiles, posts, settings)SELECT + INSERT at minimum
Stores sensitive data user can change (medical, financial, personal info)SELECT + INSERT + UPDATE + DELETE (all four)
Stores shared / read-only reference data (countries, product catalog)SELECT public; no INSERT/UPDATE/DELETE for end users

Canonical RLS policy (paste into Supabase SQL editor)

-- Enable RLS on a table
ALTER TABLE orders ENABLE ROW LEVEL SECURITY;

-- SELECT policy: users only see their own rows
CREATE POLICY "Users can read own orders"
  ON orders FOR SELECT
  USING (auth.uid() = user_id);

-- INSERT policy: users can only insert rows owned by themselves
CREATE POLICY "Users can insert own orders"
  ON orders FOR INSERT
  WITH CHECK (auth.uid() = user_id);

-- UPDATE policy: users can update only their own rows
CREATE POLICY "Users can update own orders"
  ON orders FOR UPDATE
  USING (auth.uid() = user_id)
  WITH CHECK (auth.uid() = user_id);

-- DELETE policy: users can delete only their own rows
CREATE POLICY "Users can delete own orders"
  ON orders FOR DELETE
  USING (auth.uid() = user_id);

Key gotchas:

  • USING (...) filters which rows are visible/affected for SELECT/UPDATE/DELETE.
  • WITH CHECK (...) validates inserts and updates — without it, a user could update user_id on a row they own to someone else's ID and "give it away" (or steal it).
  • The service role key bypasses RLS entirely. Never expose it to the browser. It's for server-side admin operations only.
  • If using a JWT custom claim (e.g., app_metadata.role), reference it via auth.jwt() -> 'app_metadata' ->> 'role' in policies.

Audit prompt for a Claude session

This project uses Supabase. Audit the RLS state of every table:

1. List every table in the database (via supabase migrations or `select * from
   pg_tables where schemaname = 'public'`).
2. For each table, report:
   - Is RLS enabled? (pg_class.relrowsecurity)
   - How many policies exist? (count from pg_policies)
   - For each policy: name, command (SELECT/INSERT/UPDATE/DELETE), and the
     USING / WITH CHECK expressions.
3. Flag tables that:
   - Have RLS DISABLED but store user data → CRITICAL
   - Have RLS enabled but ZERO policies for one or more of SELECT/INSERT/UPDATE/DELETE
     when the app's code calls that operation → HIGH
   - Have a policy with `USING (true)` or `WITH CHECK (true)` → HIGH (effectively no filter)
   - Have policies on UPDATE without WITH CHECK → MEDIUM (lets user reassign rows)

Output a CSV-style table: table_name | rls_enabled | select_pol | insert_pol |
update_pol | delete_pol | risk_level | one_line_recommendation.

Don't write any SQL fixes yet. Just the audit report.

2.3 Step 3 — Secrets hygiene

Goal: No secrets in code, no secrets in front-end bundles, no secrets in Git history.

3a — Is .env tracked by Git?

git ls-files | grep -E "^\.env($|\.)"

Expected output: EMPTY. Any .env file shown is committed and likely exposed.

3b — Were secrets ever committed?

git log -p --all -S "API_KEY" --source -- "*.env*" 2>/dev/null | head -50
git log -p --all -S "SECRET"  --source                2>/dev/null | head -50
git log -p --all -S "sk_live" --source                2>/dev/null | head -30   # Stripe live keys
git log -p --all -S "AKIA"    --source                2>/dev/null | head -30   # AWS access keys

Any output = a secret was once committed. Rotate it today. Removing from git history doesn't help — assume it's already scraped by bots indexing GitHub.

3c — NEXT_PUBLIC_* leaks into the browser?

grep -rn "NEXT_PUBLIC_" --include="*.ts" --include="*.tsx" --include="*.js" --include="*.jsx" . \
  | grep -i -E "SECRET|API_KEY|TOKEN|PASSWORD|PRIVATE"

Anything matching = bug. NEXT_PUBLIC_* gets bundled into the browser. Move to server-only.

3d — Hardcoded secrets in code?

grep -rEn "(sk_live_|sk_test_|AKIA[A-Z0-9]{16}|ghp_[A-Za-z0-9]{36})" \
  --include="*.ts" --include="*.tsx" --include="*.js" --include="*.json" .

Should return nothing. Matches indicate Stripe live, Stripe test, AWS access, GitHub PAT respectively.

Fix pattern

  • Anything in .env should be server-side only.
  • For Next.js, only prefix with NEXT_PUBLIC_ if it's something safe to ship to a browser (e.g., a public Supabase anon key, an analytics ID). Service-role keys / private API keys → never.
  • If a secret was ever committed → rotate it today.

2.5 The "AI made this and ship today" 5-check list

Sources: IG reels DYDvMAFIHY7 + DYcV1pdoG6X (2026-05-29). Both reels covered the same theme — security mistakes AI tools make by default that you must catch before shipping. Consolidated here as a single fast-pass checklist for any Claude/GPT-built project right before delivery.

This duplicates content from Sections 2.2, 2.2b, and 2.3 — but it’s grouped as a 5-minute "right before deploy" check rather than a full audit. Run this in addition to the rest of the runbook, not instead of it.

The 5 checks (in priority order)

  1. Service role key in client code = catastrophe. The Supabase / Firebase / etc. service-role key bypasses every RLS policy you’ve set. If it’s anywhere in NEXT_PUBLIC_*, in a client component, or in a bundled JS file — anyone who opens DevTools has full DB access. Server-side env var only. See 2.3 Secrets hygiene for the grep command.
  2. RLS turned off for debugging — and never turned back on. Classic: 3 weeks ago you flipped RLS off to test a query, forgot. Now anyone with the DB URL can read everything. Re-enable RLS + write real policies for every table. See 2.2b Supabase RLS deep dive.
  3. Login endpoint with no rate limiting. Without throttling, an attacker can try thousands of passwords per minute. Add basic rate limiting on the login route — 5 attempts per IP per minute is the floor; add account-level throttling (10 attempts per email per hour) as the next layer. 
    // Example using @upstash/ratelimit on a Next.js API route (see Section 8.6)
import { Ratelimit } from "@upstash/ratelimit";
import { Redis } from "@upstash/redis";

const ratelimit = new Ratelimit({
  redis: Redis.fromEnv(),
  limiter: Ratelimit.slidingWindow(5, "1 m"),
});

export async function POST(req) {
  const ip = req.headers.get("x-forwarded-for") ?? "anonymous";
  const { success } = await ratelimit.limit(`login:${ip}`);
  if (!success) {
    return new Response("Too many attempts. Try again in a minute.", { status: 429 });
  }
  // ... rest of login handler
}
  4. console.log statements that print passwords or tokens. Debug prints during development that never got cleaned up. They end up in browser console logs, in Vercel/Railway logs, in Sentry events. Search the codebase: 
    grep -rEn 'console\.(log|debug|info|warn|error)' --include="*.ts" --include="*.tsx" --include="*.js" --include="*.jsx" . \
  | grep -iE "password|token|secret|api_?key|jwt|session"
    Delete every match. If you actually need to log, log the user ID or event name — never the secret.
  5. .env in Git history. Adding to .gitignore AFTER an initial commit doesn’t help — the file is still in history. Run the git-log check from 2.3 Secrets hygiene. If anything shows up, rotate every key that was ever in there, today. The file isn’t "removed" until you rewrite history AND rotate the secrets.

Frontend-only validation is not validation (related but separate)

Source: reel DYDvMAFIHY7. AI tools commonly add Zod / yup / react-hook-form validation on the form, no validation on the API route handler. A technical user opens DevTools, sends the request directly with bad data, and the backend accepts whatever. Backend validation is mandatory; frontend validation is UX.

  • For every API route that takes input: validate the body server-side with the same schema you use on the client. Zod schemas work both places — share them.
  • Pattern: define schema once in src/schemas/<feature>.ts, import on both client and server, run schema.parse() on the server.
  • Audit grep: find routes that accept JSON without parsing it through a schema: 
    grep -rEn 'await req\.json\(\)' --include="*.ts" --include="*.tsx" .
# For each: confirm the result is passed through a Zod/yup/io-ts schema BEFORE
# being used. If used directly → backend validation missing.

5-check audit prompt

Run a fast 5-check pre-ship security audit on this project. Don’t do a full audit
— just check these 5 specific things:

1. Service role key exposure: grep for SUPABASE_SERVICE_ROLE_KEY, FIREBASE_ADMIN
   patterns, or similar privileged keys. Report any that appear in client code,
   NEXT_PUBLIC_ env vars, or any file that gets bundled to the browser.

2. RLS status: list every table in the schema. For each, report whether RLS is
   enabled. Flag any tenant-scoped table with RLS disabled.

3. Login rate limiting: find the login API route. Report whether it has rate
   limiting (look for @upstash/ratelimit, express-rate-limit, custom middleware).
   If none, flag as CRIT.

4. Console.log of secrets: grep for console.log statements containing variables
   named password / token / secret / api_key / jwt / session. Report file:line
   of each match.

5. .env in git history: run `git log -p --all -S "API_KEY" -- "*.env*" | head -50`
   and similar for SECRET, sk_live, AKIA. Report any matches and recommend
   rotation.

Output: a 5-row table { check_number, status (PASS / FAIL / CANT_TELL),
file:line evidence, recommended action }.

Don’t change anything. Just the audit.

2.6 Leaked-secret incident response (rotate first, scrub second)

Source: IG reel DXV91nNivPl (2026-05-30). The DevOps interview scenario: "you accidentally committed AWS keys to a public repo, ran git revert and pushed again — did that solve it?" No — and the order of operations matters more than most teams realize.

Why git revert doesn't help

  • git revert creates a new commit that undoes the change. The original commit is still in history. Anyone runs git log -p and reads the secret in plaintext.
  • Bots scan every public push on GitHub in real time. AWS, GitHub, GitLab, Datadog, and dozens of attackers’ bots index commits within seconds.
  • AWS itself runs a scanner — they’ll email you a warning. But by then, an attacker has usually already tried the key.
  • "I made the repo private" → doesn’t help. Cached commits exist on GitHub’s side, on attacker’s side, and once a secret was public for any length of time, treat it as compromised forever.

The 3-step response (in this order — order is mandatory)

  1. ROTATE FIRST — before touching git. The key is compromised the moment it hit GitHub. Every second between commit and rotation is a window for an attacker. Don’t batch — rotate as the first action.
    • AWS: IAM → Users → Security Credentials → revoke access key → generate new one. Update your .env, redeploy.
    • Stripe: Dashboard → Developers → API Keys → roll the key.
    • GitHub PAT: Settings → Developer settings → Tokens (classic) → Delete + regenerate.
    • Supabase: Project Settings → API → Generate new service_role key.
    • OpenAI / Anthropic: Console → API keys → revoke + generate.
    • Database credentials: change the password on the DB itself. If it’s Supabase: Settings → Database → reset password.
  2. Scrub history second. Now that the old key is dead, remove it from git history so future contributors and scanners don’t see it. 
    # Option A: BFG Repo-Cleaner — fastest for credential strings
# (https://rtyley.github.io/bfg-repo-cleaner/)
brew install bfg
bfg --replace-text passwords.txt --no-blob-protection your-repo.git
# passwords.txt format (one per line):
#   sk_live_oldkey_here==>***REMOVED***
#   AKIAIOSFODNN7EXAMPLE==>***REMOVED***

# Option B: git-filter-repo — more flexible, more steps
# (https://github.com/newren/git-filter-repo)
pip install git-filter-repo
git filter-repo --invert-paths --path .env --force

# Then force push (rewrites history):
git push --force --all
git push --force --tags

# Notify all collaborators to re-clone — old clones still have the secret
  3. Add prevention — set up pre-commit hooks so it can’t happen again. 
    # Install gitleaks (https://github.com/gitleaks/gitleaks)
brew install gitleaks

# Add to project as a pre-commit hook (.git/hooks/pre-commit):
#!/bin/sh
gitleaks protect --staged --redact --verbose
if [ $? -ne 0 ]; then
  echo "❌ Secrets detected. Commit aborted."
  exit 1
fi

# Or use TruffleHog (https://github.com/trufflesecurity/trufflehog)
brew install trufflehog
trufflehog git file://. --since-commit HEAD --only-verified

What people commonly do WRONG

  • WRONG git revert + push — the secret is still in the reverted commit's history.
  • WRONG Delete the file + commit — the file is still in every prior commit.
  • WRONG Make the repo private — secret was public for X seconds/minutes; assume scraped.
  • WRONG Scrub history first, rotate later — gives attacker more time before key dies.
  • RIGHT Rotate → scrub → force push → install pre-commit hook → notify team to re-clone.

The "I'm not sure if there's a secret in there" pre-flight scan

Run this on any repo you suspect:

# Scan entire git history with gitleaks
gitleaks detect --source . --verbose --redact

# Scan with trufflehog (only "verified" = actually-valid keys, less noise)
trufflehog git file://. --only-verified

# Specific patterns via git log -S (poor man's scan)
for pattern in "sk_live_" "sk_test_" "AKIA" "ghp_" "gho_" "xoxb-" "AIza"; do
  echo "--- $pattern ---"
  git log -p --all -S "$pattern" | head -20
done
The hard truth: rewriting git history breaks collaborators’ clones. If your repo has multiple contributors, you need to coordinate the force-push and have everyone re-clone. That coordination overhead is real — which is why preventing the leak via pre-commit hooks is far cheaper than fixing it after.

2.7 OWASP ZAP pre-launch scan

Source: IG reel DZyEXA6vDXs (2026-06-20, @mattmurphyai). The useful addition is operational: run a real web-app scanner before the first user signs up, then triage critical/high findings first instead of drowning in the whole report.

What ZAP is good at

  • OWASP ZAP is a free, open-source dynamic application security scanner.
  • It crawls pages, submits forms, probes API endpoints, and flags common issues: XSS, SQL injection, missing security headers, open redirects, exposed sensitive data, and auth/session misconfigurations.
  • It finds the same broad classes of issues automated internet scanners look for. Better that you find them before bots do.

Safe default workflow

  1. Run against staging or a disposable preview deployment first, not production with real user data.
  2. Use baseline/passive scan for normal client sites; active scan only when you control the target and can tolerate form submissions / test traffic.
  3. Fix findings by severity: Critical/High first (injection, auth bypass, sensitive exposure), then Medium/Low as scheduled hardening.
  4. Keep the report as delivery evidence: date, target URL, scan mode, high/critical count, and fixed items.
# Baseline passive scan (safe first pass; official ZAP container)

3. OWASP-grounded API security claims (fact-checked)

From the @jordan_kodes Instagram reel on 2026-05-02 (DXz5iIwxiuF). Saved at ~/asibrain/links/2026-05-02-api-security-3-things.md.

Claim 1: "Open endpoints — if code doesn't check who's making requests, anybody can hit your data"

TRUE

  • OWASP API Security Top 10 (2023): API1 BOLA (Broken Object Level Authorization) + API2 Broken Authentication.
  • Important nuance: authn ≠ authz. An endpoint can require login and still let user A read user B's data.
  • Mitigation: every object-level read must check current_user.id == resource.owner_id (or via a role/permission system).

Claim 2: "No pagination = DB dump"

TRUE BUT MISLEADING

  • Pagination alone is not a security control. Without rate-limiting, an attacker just loops ?page=1...N.
  • Real mitigations: (a) per-user data filtering on every list endpoint, (b) rate-limiting per IP / user / API key, (c) hard page-size cap (clamp ?limit=10000 to 100), (d) authorization on every row returned.
  • Pagination is fundamentally a performance / UX feature. The closest OWASP mapping is API4 Unrestricted Resource Consumption.

Claim 3: "Excessive error messages tell attackers how your system works"

TRUE

  • OWASP Web Top 10 (2021): A05 Security Misconfiguration; OWASP API Top 10: API8.
  • Raw stack traces leak: database engine + version, ORM + framework versions (CVE matching), file paths, library versions.
  • Mitigation: production returns a generic 500 Internal Server Error + a request ID. Full trace goes to your logging system only (never to the client).

4.4 IP / Trademark check before you fall in love with a name

Source: IG reel DYpK8fsTKUe (2026-05-29). Most "naming disaster" stories — cease-and-desist letters, app store removals, domain ransom demands — could’ve been prevented by a 10-minute search before the founder fell in love with the name.

The 4-step name check (do this BEFORE you buy the domain)

  1. Plain Google search — exact name + obvious variants. Are there companies, products, popular indie projects already using it? Quick "is this name already known for something else?" sanity check.
  2. Trademark databases — search where your clients / your business operates:
    • Israel: il-trademarks.justice.gov.il (רשם סימני המסחר)
    • EU: EUIPO
    • US: USPTO TESS
    • International: WIPO Global Brand Database — covers many jurisdictions in one search
    Search by exact name + close variants. A registered trademark in the same category (Nice classification) is a strong block.
  3. Domain + handles availability — even if the name is legally clear, if name.com is taken by an active business, you’ll be confused with them forever. Quick check: namecheckr.com, Instabase, or just typing the name into the relevant domain registrars and Twitter/Instagram/TikTok search.
  4. App store check (mobile only) — search Apple App Store + Google Play for the exact name. App stores enforce naming uniqueness more strictly than the web, and a duplicate will be rejected at review.

When this matters for Asi specifically

  • Every client project that gets a brand-new name — Bashier, gan-tair, eishoron, etc. all started somewhere. Have the client run the 4-step check before they commit to a logo or domain. Cost: 15 minutes. Cost of skipping it: ranges from awkward to legal letter.
  • Asi’s own products — if MasterOrder, the AliExpress affiliate bot, or any future project gets a public-facing name, run the check first. Same for Giggsi if it ever comes back.
  • "asi brain shared" — this is a personal repo name with a personal domain, so trademark risk is essentially zero. But for any product-level naming, the rule applies.

Red flags during the check

  • Trademark exists in the same category (same Nice class) → strong block.
  • Trademark exists in different category → usually fine, but if it’s a famous brand (Apple, Google), they can still come after you under "famous mark" doctrine.
  • Cease-and-desist letters in the company’s history (Google "[name] cease and desist") → they’re known to enforce. Skip the name.
  • Many small businesses with similar names → "confusingly similar" risk. Pick a more distinctive name.

What to do if the name is taken

  • Pick a different name. 90% of the time this is the right answer. Brand-name love is sunk cost.
  • Pick a different category. If the trademark is for "Acme Coffee" and you’re building "Acme Project Management", you might be legally fine — but get a lawyer to confirm.
  • License or buy. Only if the name is genuinely critical and the holder is willing. Rare.

5. Multi-tenancy architecture (SaaS / multi-org)

Source: IG reel DY4jQHeR4Gb (2026-05-29) — a follower was building a school management system: 50 schools, 20K users, 3 portals per school (admin / staff / students). The reel's framing was the right framing: "Multi-tenancy is not a feature, it's an architecture decision. Make it before you build, not after."

Asi asked: "verify, extend, add to the doc as clear instructions for big projects." Verified against current (2026) production patterns; extended with the practical pitfalls the reel didn't cover.

When this section applies: any client project where multiple independent organizations / businesses / schools / accounts use the same app but must not see each other's data. Examples: SaaS platforms, agency tools, school systems, marketplaces with multiple sellers, multi-clinic medical systems, multi-restaurant ordering apps (yes — Giggsi's old digital-menu would have qualified). If you're building for one company with one team, skip this section.

5.1 The 3 reel rules (verified — these are correct, but incomplete)

  1. Add tenant_id to every table. Student table, attendance table, fee records — every single row needs to know which org it belongs to. ✅ Confirmed correct — this is the dominant 2026 pattern across all production multi-tenant SaaS guides.
  2. Enforce isolation at the database level, not the app code. Use Row-Level Security so the DB itself blocks cross-tenant access. App code is the first line; DB is the last. ✅ Confirmed correct — RLS adds 1–5% overhead, removes entire categories of app-code bugs from the security surface. See Section 2b — Supabase RLS for canonical policy syntax.
  3. Design schema for actual access patterns. Students queried by school, attendance by date, fees by status — each needs its own index. ✅ Confirmed correct — "20K users is nothing for Postgres; bad schema makes 400 users feel slow."

5.2 What the reel missed (critical additions)

Addition 1 — How does the app tell Postgres which tenant?

This is the most fragile part of multi-tenant RLS — not the policies themselves, but how reliably your app sets the tenant context on every query. Three common patterns:

PatternHow tenant is identifiedHow RLS gets itWhen to use
Subdomainacme.yourapp.com vs beta.yourapp.comMiddleware resolves subdomain → tenant lookup → set SET LOCAL app.current_tenant = '...' on each requestBest for B2B SaaS with clear org boundaries (Asi's typical client)
JWT claimtenant_id in the auth tokenSupabase's auth.jwt() ->> 'tenant_id' in policiesBest for Supabase Auth — already built-in
Path prefix/org/acme/dashboardMiddleware extracts org slug → same as subdomain patternFallback when subdomains are hard (consumer-facing, no DNS control)

Addition 2 — FORCE ROW LEVEL SECURITY (the trap)

Teams set up RLS, write policies, test → it works. Then in production, the table owner can bypass policies entirely. Result: an RLS-enabled table that's still wide open from the admin role.

Always run this:

ALTER TABLE students ENABLE ROW LEVEL SECURITY;
ALTER TABLE students FORCE ROW LEVEL SECURITY;  -- The critical second line

The FORCE variant makes policies apply to the table owner too. Without it, anyone connecting as the schema owner sees everything regardless of policies.

Addition 3 — PgBouncer + RLS gotcha

If you're behind PgBouncer (Supabase production, self-hosted scaling, etc.) in transaction mode, it resets session variables between transactions. If your tenant context is set via SET LOCAL in a session variable, it gets reset — RLS then runs with no tenant context and returns either everything or nothing.

Fixes:

  • Use session mode in PgBouncer (fewer connections, but session vars persist).
  • OR set the tenant context inside every transaction explicitly: BEGIN; SET LOCAL app.current_tenant = '...'; ... ; COMMIT;.
  • OR reference the JWT directly in policies (Supabase pattern — auth.jwt() ->> 'tenant_id') so no session var is needed.

Addition 4 — Indexing

Multi-tenant tables need composite indexes leading with tenant_id:

-- BAD: index doesn't help RLS filter to find the right tenant first
CREATE INDEX idx_students_grade ON students(grade);

-- GOOD: tenant_id leads, so the RLS scan starts narrow
CREATE INDEX idx_students_tenant_grade ON students(tenant_id, grade);

-- For every common query pattern:
CREATE INDEX idx_attendance_tenant_date  ON attendance(tenant_id, date);
CREATE INDEX idx_fees_tenant_status      ON fees(tenant_id, status);

Without tenant_id leading, Postgres scans the full index then filters — fine at 1K rows, painful at 1M.

Addition 5 — Connection pooling and tenant routing

At scale (50+ tenants, high traffic), don't run all tenants through the same connection pool. Two patterns:

  • One pool, all tenants — simple, but a slow query from tenant A can starve tenant B. Good up to ~100 active tenants.
  • Pool-per-tenant or pool-per-bucket — partition tenants into N buckets by hash; each bucket has its own pool. A misbehaving tenant only affects their bucket-mates.

Addition 6 — Backup / restore boundaries

Single-DB multi-tenancy makes backup easy but tenant-level restore hard. If one school says "restore our data to last Tuesday", you can't just restore the DB — you'd overwrite all 49 other schools. Build a tenant-level export/import path early.

5.3 The 3 multi-tenancy models — pick before you build

ModelHowProsConsWhen
Single DB, shared schema 2026 default One Postgres DB. All tenant tables have tenant_id. RLS enforces isolation. Cheap. Easy to onboard tenants. Easy to add schema changes (one migration). Noisy-neighbor risk. Tenant-level backup is harder. Compliance audits may push back. Start here for 99% of projects. Only move off this if you hit a real constraint.
Single DB, schema-per-tenant One DB, but each tenant has its own Postgres schema (tenant_acme.students). Stronger isolation by accident. Tenant-level backup easier. No tenant_id column needed. Migrations × N tenants — schema drift is real. Tooling support varies. Regulated industries (health, finance) where shared-schema is a non-starter.
DB-per-tenant Each tenant gets their own Postgres instance. Strongest isolation. Per-tenant scaling. Easy "delete tenant." Expensive. Onboarding adds infrastructure. Cross-tenant analytics painful. Enterprise tier only — usually for tenants paying >$1K/mo.

6. Payments architecture (Stripe — idempotency / ledger / webhooks)

Source: IG reel DY1g56bk9_o (2026-05-29). The reel walked through 4 progressively-better versions of a payment system, each one fixing a real failure mode of the previous. This is the architecture every shipped payments integration needs — anything simpler is a future incident.

Relevance for Asi specifically: any client project that involves charging users (a subscription, a one-off purchase, a marketplace, even a tip jar) needs this. The naive "JS sends to Stripe, server marks order paid" approach works for hackathons and ships double-charges in production.

6.1 Version 1 — the naive approach (what AI defaults to)

The default flow that Claude / GPT writes if you say "integrate Stripe":

  1. User enters card details in the browser.
  2. Stripe.js library collects card details securely and sends them directly to Stripe (your server never sees raw card data — good).
  3. Stripe processes the payment, returns a response to your server.
  4. Your server marks the order as paid in the database.
  5. Send receipt email.

Why it breaks: if the user's request times out (Wi-Fi hiccup, slow server) and they retry, Stripe charges them a second time. Now you have a duplicate transaction and an angry customer. This will happen. Not "might" — "will." Network is unreliable; users press buttons twice.

6.2 Version 2 — idempotency keys

Fix the duplicate-charge problem.

  1. The client generates a unique UUID per payment attempt (the "idempotency key").
  2. That UUID is sent with the request.
  3. Your server stores the key in a database row before doing anything else (a check + insert in one transaction).
  4. If the same key shows up again — return the stored result instead of charging again.

What this fixes: retries are now safe. The user could double-tap submit, lose Wi-Fi, refresh the page — the server only charges once.

Stripe also supports idempotency natively: pass Idempotency-Key: <uuid> as an HTTP header on the request to Stripe — Stripe itself will refuse to double-charge. Belt and suspenders: do both (server-side dedupe + Stripe-side dedupe).

6.3 Version 3 — immutable ledger (event log, not status row)

Fix the audit-trail problem.

A real payment has a lifecycle: initiated → authorized → captured → maybe refunded → maybe disputed 3 months later. If you keep updating one status column on one row, you throw away the audit trail. When a regulator or finance person asks "what happened on this payment?", you have nothing to show.

Fix: every state change is a NEW row. Append-only.

idpayment_idevent_typeamountcreated_at
1pi_abc123payment_initiated$50.002026-05-29 10:00:00
2pi_abc123payment_authorized$50.002026-05-29 10:00:02
3pi_abc123payment_captured$50.002026-05-29 10:00:05
4pi_abc123refund_initiated$20.002026-06-15 14:30:00
5pi_abc123refund_completed$20.002026-06-15 14:30:08

The "current status" of a payment is computed from the full event history — not stored as a single field. If events arrive out of order (which happens with webhooks under load), your system doesn't get confused — it looks at the full timeline.

6.4 Version 4 — webhooks (don't sit and wait)

Fix the asynchronous-reality problem.

Payments aren't synchronous. You send to Stripe, get a pending back. The actual authorization might come 10 seconds later. The capture might happen the next day. Your server can't sit there waiting.

Fix: Stripe sends webhook events to your server every time a payment status changes.

Your webhook handler must:

  1. Verify the signature — confirm the message is really from Stripe (compare the Stripe-Signature header against the webhook secret). Otherwise attackers can spoof "payment completed" webhooks.
  2. Check the event ID — Stripe might deliver the same event twice. Look up the event ID in your ledger; if it's already there, return 200 OK and skip.
  3. Append a new row to the ledger — never update an existing row.
  4. Return 200 OK quickly (under 5 seconds). If Stripe doesn't get 200, it retries. If your handler is slow, you get retry storms.

6.8 Generalizing: any multi-step write operation (orders, signups, etc.)

Source: IG reel DYe7hbPiqtb (2026-05-30) — Amazon-style order placement. The same pattern that makes payments work safely also applies to any operation that needs to do multiple things on submit: order placement, user signup with notifications, content publishing with indexing.

The decision that matters: "must finish" vs "eventually OK"

Take the Amazon order-place example. Place Order kicks off 6 jobs:

  1. Charge credit card
  2. Reserve inventory (so nobody else takes the last one)
  3. Save order to database
  4. Send confirmation email
  5. Notify warehouse to ship
  6. Update recommendation engine

The wrong design: do all 6 in sequence before showing "Order Placed". User waits 1.5+ seconds. If any step fails (e.g. email service is down), the whole order errors — but the payment already succeeded. User retries → double charge.

The better design: split jobs into 2 buckets.

Must finish BEFORE "Order Placed"Can run in background after
1. Charge card (or authorize)
2. Reserve inventory
3. Write order to DB with status="confirmed"		 4. Send confirmation email
5. Notify warehouse
6. Update recommendations
If any of these fails, "Order Placed" is a lie. Must succeed before returning. If any of these fails, the order is still real. Retry the background job; user is unaffected.

The single most important question

"What must be true before we can honestly tell the user this action succeeded?"

Anything outside that core must go to a background queue. Otherwise you’re lying to users (or making them wait unnecessarily, or losing them to duplicate-submission errors).

The trap with background queues

The reel called this out: "Email worker stops working at 2am. Customer never gets their confirmation. Calls support. You don’t notice until tickets pile up."

Background jobs MUST be monitored — otherwise eventual consistency becomes never-consistent. Required:

  • Queue depth alert — if jobs pile up faster than they’re processed, page someone. Common threshold: queue depth > 1000 OR oldest-job-age > 10 min.
  • Dead-letter queue (DLQ) — after N failed retries, move the job to a DLQ. Don’t silently drop. Daily report of DLQ contents.
  • Per-job-type metrics — separate dashboard for "email send rate" vs "warehouse notify rate". If only one job type is failing, you find it fast.
  • End-to-end test — synthetic order every 15 min that goes through the full pipeline. If the confirmation email doesn’t arrive within 2 min, alert.

Concrete decision framework

For any multi-step write operation in your app, classify each step:

QUESTION 1: If this step fails AND we tell the user "success", what is the
            blast radius?
- "User is charged but no order exists" → MUST-FINISH (sync)
- "User got a confirmation email twice" → eventual-OK (async)
- "Recommendation engine is 5 minutes stale" → eventual-OK (async)
- "Warehouse doesn’t ship for 30 seconds" → eventual-OK (async, BUT monitored)

QUESTION 2: How long does this step take in the 95th percentile?
- < 100ms → fine inline
- 100ms – 1s → fine inline if must-finish, otherwise push async
- > 1s → always push async (unless legally must-finish like payment)

QUESTION 3: What’s the failure rate?
- > 1% → cannot be inline-must-finish (user-visible errors too often).
  Either redesign to remove the dependency, or push async with retry.

OUTPUT: split steps into 2 buckets (sync must-finish / async eventual)
+ for async, define retry policy + DLQ + monitoring metric per job type.

7. Feed architecture (Instagram-style — fan-out / push-pull / Redis)

Source: IG reel DYCbWHGD1r1 (2026-05-29) — a clean 4-version progression for building a home feed (Instagram, X, threads, any "follow people → see their posts" app). Same structure as Section 12 (Payments architecture): each version fixes a real failure mode of the previous.

When this section applies: any project with a follow graph and a feed. Examples: social apps, community platforms, multi-author blogs/newsletters with subscribers, internal tools where staff "follow" projects, marketplaces with seller follows. If your project has thousands of users producing content that gets shown to followers, you need this architecture before you have it as a problem.

7.1 Version 1 — Naive: query-on-read

The default flow Claude/GPT writes for "show me a feed":

  1. User opens app.
  2. Server runs one big SQL query: "give me all posts from everyone this person follows, ordered by time, limit 50."
  3. JOIN posts × followers, sort, return.

Works fine for: first thousand users. Single user follows a handful, posts are sparse, query is fast.

Where it breaks: the average user follows ~200 people. Power users follow ~2,000. Each opens the app ~30× a day. Even with good indexes, the query has to fetch + merge + filter + rank recent posts across thousands of followed accounts every single time. Database melts.

7.2 Version 2 — Fan-out on write

Flip the model. Do the work at write time, not at read time.

  1. User posts a photo.
  2. Server figures out who follows that user.
  3. For each follower, append the new post ID to that follower's "inbox" (a per-user feed list, often in Redis).
  4. When a follower opens the app: fetch their inbox (cheap cache read), then fetch the actual post details from Postgres.

Now read is a single cheap key lookup. The expensive part — finding posts to show — was already done at write time.

Where this still breaks: celebrities. One user has 80M followers. They post one photo → 80M inbox writes hit your queue. The whole system stalls behind one Ronaldo sneeze.

7.3 Version 3 — Hybrid push/pull (the part most teams get wrong)

The mistake: picking one model for everyone. You don't have to.

User typeStrategyWhy
Normal user (≤ 100K followers)Push — fan-out on write to follower inboxesFew followers per post — cheap to push. Read stays fast.
Celebrity (> 100K followers)Pull — don't push at all. Keep a per-celebrity "author feed cache" with their recent posts. At read time, merge it in.Pushing to millions of inboxes is the disaster. Pulling a small list of celebrities a user follows at read time is cheap.

At read time:

  1. Fetch user's pre-built inbox (normal users' posts).
  2. Fetch the celebrity author-feed caches for each celebrity this user follows.
  3. Merge by time, return top 50.

The 80M-write problem disappears. The threshold (100K) is arbitrary — pick whatever matches your actual follower distribution.

7.4 Version 4 — Move feeds to Redis (separate the load)

In V3, inboxes are still in your main database. Millions of temporary feed writes still hit the same DB that holds your real post data.

Separation:

  • Postgres — source of truth for actual posts, users, follows, comments.
  • Redis — hot feed inboxes. Each user's inbox is a sorted set (ordered by timestamp), capped at ~800 entries ("no one scrolls past 800").

Result:

  • Feed loads drop to single-digit milliseconds.
  • Main DB barely sees feed traffic — basically free scaling for reads.
  • Inbox eviction is automatic (the sorted-set cap drops oldest).

7.8 Real-world variations to consider

  • Ranking, not just chronological — modern feeds aren't pure time-sorted. They use ML ranking. You can still use the same fan-out architecture; the ranking layer sits on top of the merged feed before returning to the user.
  • Read receipts / seen state — store per-user "last seen" timestamp; truncate inbox by that to avoid re-showing old posts.
  • Pre-warm inbox for new follows — when user A follows user B, decide: do you backfill A's inbox with B's recent posts? Most apps don't (cheap UX cost; lets new follows feel fresh on next post).
  • Deleted posts — when a post is deleted, you may have already pushed it to millions of inboxes. Either: (a) lazy-delete (filter out at read time), (b) eager-delete (tombstone propagation). Lazy is cheaper but leaves stale entries.
  • Privacy changes — private accounts that become public, blocks, mutes — same problem as deletes. Lazy filter at read time is the standard answer.

8.7 Docker for non-Vercel workloads (the small-image discipline)

Source: IG reel DXYh9CHihnt (2026-05-29). The reel framed a junior-developer interview scenario: "a 2GB Docker image — storage is cheap, who cares?" The right answer is not about storage; it's about every deploy pulling 2GB, every container spinning up 2GB, every traffic spike multiplying the cost, and every extra package being an attack surface.

When this matters for Asi: Vercel handles Docker invisibly — you don’t need this for client Next.js projects. Reach for this section when: (a) you move a trading bot from Mac mini to Railway/cloud, (b) a client asks for a self-hosted/on-prem deployment, (c) you build an MCP server you want others to run.

The 3 disciplines (verified, universally true)

  1. Multi-stage builds. Stage 1 builds the app with all dev dependencies (TypeScript compiler, build tools). Stage 2 copies only the compiled output into a clean minimal final stage. Build tools never make it to production — saves size AND removes attack surface.
  2. Small base image. Don’t use node:18 (~900 MB). Use node:18-alpine (~50 MB) or node:18-slim (~150 MB). For Python: python:3.12-slim or python:3.12-alpine. For zero-shell production: gcr.io/distroless/nodejs or gcr.io/distroless/python3 — no shell, no package manager, no attacker tools.
  3. Always have a .dockerignore. Same idea as .gitignore: keep node_modules, .git, test files, local .env out of your image. Most "huge image" surprises are someone accidentally copying node_modules in.

Minimum-viable Dockerfile for a Python trading bot

# Stage 1: build dependencies in a fat builder
FROM python:3.12-slim AS builder
WORKDIR /build
COPY requirements.txt .
RUN pip install --user --no-cache-dir -r requirements.txt

# Stage 2: minimal runtime
FROM python:3.12-slim
WORKDIR /app
COPY --from=builder /root/.local /root/.local
COPY . .
ENV PATH=/root/.local/bin:$PATH
ENV PYTHONUNBUFFERED=1
CMD ["python", "bot.py"]

8.8 When to graduate from Vercel (and where to)

Source: IG reel DYzc-WUAOlA (2026-05-30). "Hitting the 10-second timeout on Vercel hobby" isn’t a bug — it’s the platform telling you it’s time for a bigger house.

Vercel’s real limits (Hobby plan)

  • 10-second function timeout on Hobby (60s on Pro, 300s on Enterprise — but cold-start fees stack).
  • Serverless-only execution — no persistent processes, no in-memory state across requests, no background workers (without Vercel Cron).
  • 4.5MB request body (default, configurable but limited).
  • Stateless filesystem — wiped on every deploy and between cold starts. Don’t write to disk.

Fine for: landing pages, marketing sites, dashboards, CRUD apps, anything API-mediated that responds quickly. Hits the wall for: file processing, video transcoding, anything iterating over >1000 rows, long-running AI calls (OpenAI streaming over 10s), background jobs, websockets.

The graduation options (when Vercel isn’t enough)

PlatformBest forWhat you give up
Railway Persistent servers, long-running background jobs, cron, websockets. Best successor to "Vercel hit its limits." You manage a "server" again (still pretty automatic). Less integrated edge network.
Render Same as Railway + managed Postgres/Redis included. Good when you want one bill for hosting + DB. Slightly more setup overhead than Railway.
Fly.io Apps that need to be CLOSE to users worldwide (low latency, edge compute). Best for a global audience. More complex networking model. Steeper learning curve.
DigitalOcean App Platform / Droplet Cheapest persistent VPS. Full control, low managed-features count. Good for self-hosted PocketBase, n8n, etc. You’re back to traditional Ops a bit more.

The split-stack pattern (don’t pick one, pick both)

Most production apps end up with this layout:

┌──────────────────┐        HTTPS         ┌──────────────────────┐
│   FRONTEND       │ ───────────────────→ │   BACKEND / WORKER   │
│   (Vercel)       │                      │   (Railway or Render)│
│                  │                      │                      │
│ - Pages          │                      │ - Long-running jobs  │
│ - Static assets  │                      │ - Cron tasks         │
│ - Quick API      │                      │ - Background queues  │
│ - Marketing site │                      │ - Websockets         │
└──────────────────┘                      └──────────────────────┘
        │                                            │
        └─────────────┬──────────────────────────────┘
                      ↓
                 ┌─────────────┐
                 │  DATABASE   │
                 │ (Supabase / │
                 │  Neon)      │
                 └─────────────┘

Both halves talk over HTTPS — there’s no coupling that requires same-host deploys. This is what every production app ends up being eventually, whether the team plans it that way or not.

"When should I split?" decision tree

You’re still on Vercel-only — when to consider splitting?

[ ] Vercel timeout errors in the logs (10s on Hobby, 60s on Pro)
    → split. Move long-running work to Railway/Render.

[ ] Need cron jobs more frequent than Vercel Cron allows
    → split. Railway has unlimited cron.

[ ] Need a websocket connection that stays open
    → split. Vercel doesn’t do persistent connections; Railway does.

[ ] Need a background queue (BullMQ, etc.)
    → split. Vercel functions can’t host queue workers.

[ ] Need to write to local disk (e.g., temp file before upload to S3)
    → split. Vercel filesystem is stateless.

[ ] Doing heavy CPU work (image processing, AI streaming > 30s)
    → split. Vercel pricing punishes you per request-second.

If 2+ of these are true → split now, not later. The migration gets harder
the more code depends on Vercel-isms.
For Asi specifically: the trading bots running on the Mac mini are exactly the Railway-shaped workload — long-running, persistent, websocket-heavy. If you ever move them off the Mac mini, Railway is the answer. Client Next.js projects stay on Vercel for the frontend, with optional Railway backend if they need any of the above. Don’t over-engineer: stay on Vercel-only as long as nothing’s actually broken.

8.9 CI/CD maturity ladder — start small, grow when you have users

Source: IG reel DYh_2F6j2Jb (2026-05-30). The reel framed it well: "Big tech CI/CD pipelines are overkill for a solo vibe coder. But at a bare minimum, you need some kind of test that shows you when your system broke."

This is the maturity progression — pick your current rung, know what’s next:

StageWhat you haveWhen to add the next rung
Rung 0 — Solo, no users Push to main → auto-deploy. No tests. No monitoring. The day the first real user uses it.
Rung 1 — "Something broke" detection ⭐ (minimum bar) Sentry catches errors. Vercel previews per PR. npm test runs a smoke test before merge. When you have 10+ users you care about disappointing.
Rung 2 — Real staging Dev branch with full preview environment (Section 8.1). PR check requires Vercel preview success. Stripe in test mode on staging. When breaking things in prod costs real money or trust.
Rung 3 — Infrastructure as Code (IaC) Terraform / Pulumi / Vercel config files in git. Staging environment is a literal clone of production, built from the same code. When the cost of "we set up prod manually and now nobody remembers what" exceeds the cost of learning Terraform.
Rung 4 — Gradual rollout Canary releases (1% of users get new version, scale to 100% if no errors). Feature flags (LaunchDarkly, GrowthBook). Geo-staged rollouts (EU first, then US). When one bug affecting 100% of users costs > 1 day of dev time to fix.

The two concepts the reel mentioned worth knowing about

Infrastructure as Code (IaC) — instead of "I clicked through the Vercel dashboard to set this up," your entire infrastructure is described in files committed to git. To recreate the prod environment: terraform apply. Tools:

  • Vercel: vercel.json handles a lot already. For multi-project, use the Vercel Terraform provider.
  • Generic cloud: Terraform (the standard) or Pulumi (TypeScript-flavored).
  • Lighter: Docker Compose for self-hosted setups. Renders + Railway both let you commit a YAML config.

Gradual rollout (canary / feature flags) — instead of "deploy to everyone instantly", new versions reach a small % of users first. If errors spike, automatic rollback. Tools:

  • Feature flags: GrowthBook (open source, free), LaunchDarkly (paid, enterprise). Wrap features in if (flagOn("new_payment_flow", user)) { ... }.
  • Canary deploys (platform-level): Vercel doesn’t expose canary natively but you can fake it with feature flags + percentage gates. Cloudflare Workers + Fly.io both support fractional traffic routing.

For Asi specifically — where you are on the ladder

  • Trading bots: Rung 0–1. The Mac mini is solo, no users (only you watch them). Add Sentry-equivalent monitoring later if you care to alert on bot crashes — but otherwise current setup is fine.
  • Client Next.js projects: Rung 1–2 should be the minimum delivery standard. Sentry + Vercel preview-per-PR + a single smoke test (can we hit the homepage). Anything more is overkill until the client has paying users.
  • Big B2B clients (future): Rung 3 (Terraform) when you take on a client where ops continuity matters. Rung 4 (canary + feature flags) only for clients with > 10K users where one bad deploy = real money.
Don’t skip rungs. Adding Terraform to a 3-user app is wasted time. Adding canary to a no-monitoring app is putting a sports steering wheel on a car with no brakes. Progress one rung at a time, driven by actual pain.

8.10 Product analytics — what users actually do (you can’t guess)

Source: IG reel DY2zZvMsVzj (2026-05-31). The reel makes a real point: "One thing vibe coders constantly forget to add is product analytics." Then pitches Amplitude — that part is an ad, but the underlying need is real and almost always missing in client deliveries.

Note on terminology: "Product analytics" is different from "site analytics" (Google Analytics, Plausible). Site analytics tells you "how many visitors did /pricing get last month." Product analytics tells you "of users who signed up last week, what % completed onboarding, what % paid, where did the others drop off." Both useful — but the second is the one that tells you what to build next.

What product analytics actually answers

  • Which buttons are clicked / never clicked.
  • How long users stay on each page.
  • Where they drop off in onboarding / checkout / signup.
  • What actions a churned user took right before cancelling.
  • What % of users use each feature (so you know which features to deprecate).
  • Conversion funnels: visit → signup → activate → pay → retain.

The 3 tools worth knowing

ToolBest forCostCaveat
PostHog ⭐ Default recommendation for Asi. Open-source, self-hostable, full feature set (analytics + session replay + feature flags + A/B tests). Generous free tier (1M events/month cloud, OR self-host on a $5 VPS). Setup takes 1 hour; learn curve a couple hours.
Amplitude The reel’s pick. Industry-standard product analytics, polished dashboards. Free tier 10M events/month; paid plans expensive. Less flexible than PostHog, no self-host option, more vendor lock-in.
Plausible / Umami Lightweight site analytics (pageviews, referrers, browsers) — NOT product analytics. Privacy-friendly, GDPR-safe, no cookie banner. Plausible $9/mo. Umami self-hostable. Doesn’t answer "what did users do inside the app." Pair with PostHog for the deeper questions.

What to track (the minimum useful event set)

Track too little = no insight. Track too much = noise and event-quota bills. The right minimum:

// Identity events
posthog.identify(userId, { email, plan, signupDate });

// Lifecycle events (the funnel)
posthog.capture("user_signed_up", { source });
posthog.capture("onboarding_step_completed", { step, total_steps });
posthog.capture("first_meaningful_action", { action_name });
posthog.capture("payment_completed", { amount, currency });
posthog.capture("subscription_cancelled", { reason, days_subscribed });

// Feature usage (one event per primary feature)
posthog.capture("feature_used", { feature, context });

// Errors that reach the user
posthog.capture("error_shown_to_user", { message, page });

That’s it. Maybe 10-15 unique event names per app. Resist the urge to track every click — you’ll never look at most of it.

What to actually look at (weekly review)

  1. Funnel: signup → onboarding complete → first action → paid. Where’s the biggest % drop?
  2. Activation rate: % of new users who hit "first meaningful action" within 24h. If low, your onboarding is broken.
  3. Feature usage: sorted by % of users using each. Bottom 20% are candidates for deprecation.
  4. Churn replay: for each cancelled user, look at their last 10 events. Pattern emerges within 5–10 reviews.

For Asi specifically

  • Client projects with users (Bashier, etc. — anything past the brochure-site phase): install PostHog at delivery. 10x more valuable than the client realizes. Show them the funnel dashboard on month 1 and they’ll see why they hired you.
  • Trading bot infrastructure: not applicable (you’re the only user). Bots already log events to JSON.
  • Future SaaS / MVP launches (your own products): PostHog from day 1. Cheaper than retrofitting later, and informs every product decision.
  • Brochure / static sites: skip product analytics. Use Plausible or Umami for site stats only. Don’t over-engineer.

   - YES if: real user-facing site, brochure or app.
   - Recommend: Plausible (paid, simple, GDPR-clean) or Umami (self-host).
   - PostHog also covers this if installed.

2. Product analytics (what users DO inside the app)?
   - YES if: there’s any user account, signup, or feature with measurable use.
   - Recommend: PostHog (default), Amplitude (if budget allows).
   - Identify the 8-12 events worth tracking based on the app’s structure.

3. Output:

8.11 Global latency playbook — edge frontend + read replicas

Source: IG reel DZCzQPpRI8d (2026-06-19, @mattmurphyai). The reel’s useful claim: if the app runs from one server/DB region (for example Virginia) and users are in Singapore, Israel, Europe, etc., 3–5 second page loads are often an architecture latency problem, not a random bug.

Important framing for Asi: this is a recommendation / future scaling pattern, not a mandatory rule for every Next.js project. Do not add multi-region complexity to a brochure site, MVP, or client app whose users are mostly in one country. Use it when real traffic or product requirements show meaningful users in multiple regions and latency is hurting UX or conversion.

The 3-part pattern

LayerRecommendationWhat it fixes
Frontend Deploy static assets / frontend to Vercel or Cloudflare Pages. HTML/CSS/JS/images load from an edge location near the user instead of a far-away origin.
Database reads Add Supabase read replicas or equivalent Postgres replicas in regions near users. Read-heavy pages stop round-tripping every query to the primary DB region.
Routing Use Vercel Edge Middleware or Cloudflare Workers to route by geography. Reads go to the nearest replica; writes still go to the primary DB to keep consistency simple.

Decision rule — when to use vs skip

Use this pattern whenSkip / postpone when
Users are meaningfully split across regions: Israel + US + EU, or Asia/Australia users feel slow. Nearly all users are in Israel / one region; choose the closest single DB region instead.
The app is read-heavy: dashboards, catalogs, content, CRM views, analytics, feeds. The app is mostly writes, payments, admin mutations, or single-user backoffice flows.
You can tolerate slightly stale reads for some data or explicitly route “read after write” to primary. The product requires strict immediate consistency on every screen and the team is not ready to reason about replica lag.
Latency is measured and hurting UX: Web Vitals / server timing / logs show cross-region DB round trips. No measured latency problem yet — complexity would be premature optimization.

Implementation notes for Next.js + Supabase

  • This is not a Next.js replacement. Next.js stays the app framework; this is a deployment/data topology upgrade around it.
  • Separate read vs write paths. Queries that render public/read-heavy pages can use the nearest read replica. Mutations, checkout, auth-sensitive “save then show me the result” flows should use the primary DB or force a primary read immediately after write.
  • Protect tenant/user boundaries. Read replicas do not replace RLS, authorization checks, or correct cache keys. A fast data leak is still a data leak.
  • Prefer measurement before migration. Add timing logs around server actions/API routes and DB queries before paying for replicas.

Pre-upgrade audit prompt

This project may have users in multiple regions. Audit whether a global-latency
upgrade is worth it. Do not change infrastructure yet.

1. Identify where users are located from analytics/logs/customer data.
2. Identify the current deployment region(s): frontend host, server/API runtime,
   primary database, object storage, external APIs.
3. Measure slow paths: pages/API routes with p95 > 1s, DB queries, and external calls.
4. Classify each slow path as READ, WRITE, or MIXED.
5. Recommend one of:
   - STAY SINGLE-REGION: no real multi-region need yet.
   - MOVE PRIMARY REGION: users are concentrated somewhere else; choose a better single region.
   - ADD EDGE/CACHE ONLY: static/API caching solves most latency.
   - ADD READ REPLICAS + GEO ROUTING: users are truly multi-region and read-heavy.
6. For any replica recommendation, list read-after-write screens that must keep
   using the primary or show an explicit refresh/pending state.

Output: recommendation | evidence | expected latency win | complexity risk | next safe step.

9.2 The 4 states every screen must have (Part 2 — reel DYXxwf-BZpp)

From the same series’ Part 2. The single most important framing for AI-built UIs: every screen has 4 distinct states, and AI tools only design one of them by default.

Brief history of loading indicators (mostly cultural context)

  • 1984 — Mac: tiny wristwatch cursor. No animation.
  • 1985 — Windows: hourglass. No animation. Lasted ~20 years.
  • Late 80s — progress bars first appear. Research: 86% of people prefer them even when they’re inaccurate. (The bar is a comfort signal more than an info signal.)
  • 2001 — Mac OS X: spinning rainbow wheel ("beach ball of death"). Animated but tells you nothing — has it been 5 seconds or 2 minutes? Still technically exists today.
  • 2013 — skeleton screens conceived. Facebook adopts early. Work because your brain processes the layout while waiting for data.
  • Now — skeleton screens for whole pages; spinners for buttons / small refreshes; optimistic UI for high-confidence ops; progress bars only when duration is known.

The principle that matters

"Loaders should feel intuitive — most of the time when they’re there, you don’t even notice them. But when they’re missing, users notice and assume something is broken. When done well, people will wait longer without realizing it."

This is why the 4 states matter: if you only build "Success", every other situation becomes "something is broken" from the user’s perspective. They blame you, even when the data was just slow or empty.

Pre-deploy check (per screen)

    — see Section 9.4 for which to use)
[ ] Success — the designed UI with data. (Default — AI handles this fine.)
[ ] Error — what shows if the fetch fails? Network down, 500 from backend,
    validation failed, etc. (See Section 9.3.)
[ ] Empty — what shows if the fetch succeeds but returns no data?
    (See Section 9.3.)

For each screen, output: screen_name | loading_state | success_state |

9.3 Error states (Part 5 — reel DYr7cKLIQo6)

Unless you explicitly ask, AI-built apps tend to default to one of three bad patterns: raw stack traces dumped to the user, vague "Something went wrong", or silent failures (button click → nothing happens).

The 3 things a good error message must do

  1. Tell them what happened. Not "Error 500" — say what actually broke in user-readable terms.
  2. Tell them why. Even a short clue helps them feel in control.
  3. Give them a clear next action. "Try again," "use a different card," "contact support" — never leave them stuck.

Anti-pattern comparison

BadWhy badGood
SQLError: ER_DUP_ENTRY: Duplicate entry 'foo@bar.com' for key 'users.email' Leaks DB engine + schema. A regular user has no idea what it means. Also a security vulnerability — see Section 3, Claim 3. "This email is already registered. Try logging in instead, or use a different email."
"Something went wrong." Tells the user nothing. After a payment, they don't know if their card was charged or not — terrible for trust. "Your payment didn't go through — your card was declined. Please check your card details or try a different payment method."
(silent failure — button click does nothing, screen doesn't change) The worst kind. User has no idea if the action worked, is processing, or broke. Default AI-coded behavior when error handling is absent. Inline error near the form field that failed, plus a toast/banner for system-level errors. Always show something within 1 second of the action.

Implementation checklist for any form/action

[ ] Loading state shows within 200ms of click (spinner or skeleton)
[ ] On success: explicit confirmation (toast, redirect, or visual change)
[ ] On client validation error: inline error near the specific field
[ ] On server error: user-readable message (not stack trace) + suggested next step
[ ] Network failure handled separately ("Check your connection and try again")
[ ] Never just disable the button silently — show why it's disabled
[ ] Server errors logged server-side with request ID; UI shows the request ID
    so user can quote it to support
[ ] Payment / destructive actions: extra-explicit error wording
    ("Your card was NOT charged" vs "Payment failed")

Prompt to upgrade existing error handling

Audit this project's error handling. Find every place that:
1. Catches an error and shows the raw error message to the user
   (look for: catch(e) { setError(e.message) }, throw new Error(...) reaching UI)
2. Has a "Something went wrong" string anywhere
3. Has a form submit handler with no error UI
4. Has a button that can fail with no loading state

9.4 Error placement — toast vs modal vs inline (Part 7 — reel DY0IImqxNQ0)

The companion to 9.1. Even a great error message in the wrong place is invisible. Three placements, each for a specific use case — getting this wrong is a common AI default.

PlacementWhen to useWhen NOT to use
Toast (top/bottom, auto-dismisses) Non-critical, recoverable, transient. "Couldn’t connect, retrying." "Saved." "Copied to clipboard." Anything important. If the user looks away for 3 seconds and misses it, are they OK? If no → don’t use a toast.
Modal (center, blocks everything) User can’t continue without addressing the issue. Payment failed. Permissions error. Session expired. Always include a way forward (button: "Update payment method", "Request access", "Log in again"). Anything less than blocking. Modals interrupt and frustrate — use sparingly.
Inline (right next to the problem) The default for most errors. Form field validation, button-click failures, anything where the user’s eyes are already in the area. System-wide errors not tied to a specific element (use toast or modal instead).

The general rule

The closer your error message is to the thing that went wrong, the better.

If the user clicks "Save" and it fails, the message should appear right next to the Save button — that’s where their eyes already are. A toast at the top of the screen makes them search for the message. A modal interrupts a flow they expected to be quick.

Common AI placement mistakes

  • WRONG Toast for "payment failed" — user looks away, misses it, retries → double charge. Use modal.
  • WRONG Modal for "saved successfully" — interrupts the flow. Use toast.
  • WRONG Form-level error banner ("There were errors on the form") for field-level validation — user has to hunt for which field. Use inline per field.
  • WRONG Modal blocking everything but no action button — dead end. Always include a way forward.
  • RIGHT Inline for field validation + toast for transient system messages + modal only for "can’t proceed without this."

9.6 Empty states (Part 8 — reel DY5PkUjyhMv)

The reel framed it well: "As designers and developers we like to think about new features. But the empty state is often what your user sees first. Let's make a good impression."

The 3 kinds of empty state — each needs its own treatment

Kind 1: First-time empty (onboarding)

User just signed up, lands on dashboard, sees nothing. The default failure — leaves them stuck. Fixes:

  • Primary CTA inline — "Create your first project" right where the project list would be. Not just a small button in the corner.
  • Optional step-by-step — gamified onboarding: "Step 1 of 3 — name your project". Right for complex apps; overkill for simple ones.
  • Explain the section — even a 1-line "This is where your projects will live" reduces confusion.
Kind 2: No-results empty (search / filter)

User searched, got nothing. Don't just say "No results."

  • Repeat what they searched for — "No results for 'purple shoes'" — confirms the system understood.
  • Give them a way forward — link to clear filters, suggest alternative search, show popular categories. Anything that keeps the user moving.
  • Don't blame them — "Did you mean…?" works; "Your search returned no matches" feels accusatory.
Kind 3: Achievement empty (cleared / completed)

User cleared their inbox to zero, finished all tasks, archived all notifications. This is a celebration, not an empty page.

  • Make it feel like an achievement — animation, celebratory background, "Inbox zero! Nicely done."
  • Reward the behavior — users should look forward to reaching this state, not dread it as "broken."
  • Examples that nail this: Superhuman's empty inbox, Things 3's completed task celebration, Linear's empty backlog.

The 3-rule definition of a good empty state

  1. Tells the user why it's empty (first-time / no results / achievement).
  2. Shows what to do next — even if the answer is "go take a break."
  3. Doesn't feel broken — visual treatment, copy, illustration that says "this is intentional", not "something didn't load."

9.7 Loading patterns (Part 3 — reel DYcbCoiIKK1)

Each loading indicator triggers a different psychological response. Pick the right one for the context — getting this wrong makes users think the app is broken even when it’s working.

The 4 loading patterns and when to use each

PatternWhen to useWhat it signals to the userReal-world examples
Skeleton screen Entire page or large section loading. Layout known, data not yet there. "The shape is here, content is coming, this isn’t broken." Instagram, LinkedIn, YouTube feeds
Progress bar You know how long it takes — file uploads, downloads, installations. "Here’s exactly how far along it is + how much longer." Dropbox upload, OS installs
Inline spinner Small contained action — a button just clicked, one part refreshing. "We got it, working on it." Button "save"/"submit" spinners, partial list refresh
Optimistic UI (no loader) High-confidence operations that almost never fail. Roll back on the rare failure. "Done." Feels instant. Instagram heart-like, Twitter like, Linear status toggle

Critical anti-patterns

  • Spinner on a file upload — users assume it’s stuck. Use a progress bar. Always.
  • Skeleton screen for a button click — wrong scale. Inline spinner is the right unit.
  • Optimistic UI for a payment — if it later rolls back, the user is angry and confused. Reserve optimistic UI for ops where the failure mode is "no consequence" (likes, drag-and-drop).
  • No loader at all on a real backend call — users click again, you get double submits, see Section 6 Payments idempotency.

Decision tree (paste into your prompt to Claude)

For this loading state, pick the right pattern:

1. Is the operation typically < 100ms AND has < 1% failure rate?
   → Optimistic UI. Update the UI immediately, reconcile if server disagrees.

2. Does the user need to know "how much longer"?
   → Progress bar. Show real % when known; estimate when not.

3. Is this a whole page or a large region loading?
   → Skeleton screen. Match the actual layout shape.

4. Is this a small contained action (button, partial refresh)?
   → Inline spinner.

5. Will the operation take > 3 seconds without feedback?
   → Whatever pattern you picked, ADD a textual hint ("This usually takes
     about 5 seconds...") to maintain trust.

9.8 Partial states & graceful degradation (Part 9 — reel DY-IhhSBV9b)

The reel’s framing nails it: "When you order delivery from three different restaurants, do you expect all of them to show up at exactly the same time? And if one doesn’t show up, do you throw all the food away? Of course not."

Most non-trivial app screens are composed of independent data sources: profile from one API, feed from another, notifications from a third, ads from a fourth. Each loads and fails independently. AI tools default to either:

  • Bad #1 One big loading screen until everything is ready — the user waits behind the slowest fetch.
  • Bad #2 One big error page if anything fails — the user loses access to features that actually worked.

The principle: graceful degradation

Each section loads on its own, fails on its own, and the rest of the page is still usable.

Examples done well:

  • Instagram — stories ready, feed still loading, search ready — each independently. You can interact with stories while the feed finishes.
  • Linear / Notion dashboards — sidebar always works; chart on the right loads / fails independently. Sidebar error doesn’t break the chart, chart error doesn’t break the sidebar.
  • YouTube watch page — video loads first; comments lazy; recommendations independent. If comments are down, you can still watch.

How to actually implement it (Next.js + React 19)

// EVERY independent data source gets its own Suspense + ErrorBoundary
// React 19 streaming makes this the default pattern.

import { Suspense } from "react";
import { ErrorBoundary } from "react-error-boundary";

export default function Dashboard() {
  return (
    <div className="dashboard">
      <Sidebar />                              {/* Server Component, no loading needed */}

      <ErrorBoundary fallback={<ProfileErrorCard />}>
        <Suspense fallback={<ProfileSkeleton />}>
          <ProfileCard />                      {/* Fetches user profile */}
        </Suspense>
      </ErrorBoundary>

      <ErrorBoundary fallback={<ChartErrorCard />}>
        <Suspense fallback={<ChartSkeleton />}>
          <RevenueChart />                     {/* Fetches chart data */}
        </Suspense>
      </ErrorBoundary>

      <ErrorBoundary fallback={<FeedErrorCard />}>
        <Suspense fallback={<FeedSkeleton />}>
          <RecentActivity />                   {/* Fetches activity feed */}
        </Suspense>
      </ErrorBoundary>
    </div>
  );
}

Each component: has its own Suspense (loading) + its own ErrorBoundary (error). One slow fetch doesn’t hold up the others. One failed fetch doesn’t break the rest of the page.

The decision rule

For every screen, ask: "What’s the cost of one slow/failed section blocking the others?"

  • High cost (dashboard, social feed, profile, e-commerce listing) → graceful degradation. Per-section Suspense + ErrorBoundary.
  • Low cost (login form, checkout flow) → single state is fine. These are linear flows; partial-loading would be confusing.
  • Default for new screens with 3+ data sources → graceful degradation. It’s rarely the wrong call.

9.9 Success states & confirmation feedback (Part 11 — reel DZYfsYPv1-l)

When a user completes an action, the interface must confirm that it worked. Missing success feedback creates the worst kind of product anxiety: "Did it go through? Was I charged? Should I click again?"

The principle

Every meaningful user action needs an observable success state. The higher the stakes, the more explicit the confirmation must be.
Action typeGood success feedbackBad default
Payment / booking / irreversible actionDedicated confirmation page or panel with receipt/order ID, next step, and email expectation.Button returns to normal with no confirmation — user wonders if they were charged.
Form submit / saveInline saved indicator, toast with specific object name, or updated timestamp.Silent submit; user clicks again or navigates away unsure.
Low-risk interaction (like, star, drag card)The action itself visibly persists: liked state stays active, card remains in Done, item appears in list.Temporary animation only, then no durable visual evidence.
Milestone / major completionCelebratory state can be appropriate: completion page, progress unlocked, small animation/confetti.Overusing confetti for trivial actions, which makes the app feel noisy and unserious.

Implementation checklist for client apps

  • Define success per action: what must be true before the UI can honestly say "done"? For payments/orders, do not show success before the critical write/payment confirmation is durable.
  • Make it persistent enough: a 2-second toast is not enough for high-stakes actions. Show a durable confirmation page/row/status that survives refresh.
  • Prevent duplicate actions: disable the submit button while pending, use idempotency keys for writes/payments, and show a clear post-success state.
  • Match the emotional weight: subtle inline feedback for tiny actions; explicit confirmation for money, bookings, destructive actions, and first milestones.
  • Include recovery path: after success, provide the next useful action: view receipt, manage booking, create another item, go back to dashboard.

12. Bot code-quality patterns we’ve learned

Real bugs and fixes we've shipped in the trading bots. Not security per se, but pattern-spotting that transfers to client projects too. Each is worth checking against new code.

PatternWhat we fixedLesson for next time
Exchange-timestamp vs monotonic-time OrderFlowEngine was using time.monotonic() for trade timing, causing live ≠ paper signal divergence. Replaced with exchange-supplied trade timestamps. For anything time-sensitive that needs to match a replay or another engine, use the canonical timestamp from the source — never local clock.
Equity measurement Bot performance was measured by cycle count and total_profit accumulator. Wrong — partial fills inflate it. Switched to equity_end - equity_start. For any performance metric, measure the bottom-line state change, not an event counter.
Frozen-pot equity bug compute_total_equity() dropped pending-LIMIT capital because margin or frozen short-circuited. Fixed: sum both fields. Python's or is value-short-circuit, not None-coalesce. Use x if x is not None else y when both might be zero.
Drift-aware staleness Stale-buy detection compared price to bid instead of bid - N*tick, so every BUY was canceled every 3 min → lost queue position. Added drift threshold + longer timeout. If you cancel-and-replace orders, you lose your queue position. Make staleness rules tolerant unless price has actually moved meaningfully.
Trail-state interference with reset Trail logic re-fired infinitely and interfered with stuck-SELL recovery. Fixed with single-fire flag + gated on not awaiting_reset_exit_fill + cleared in _record_sell_reset. State-machine flags need explicit reset paths. Don't trust other state to clear yours.
WS connection split per channel (Bitunix) Single WS connection for multiple channels silently dropped order-flow signals on big-cap coins. Required 1-connection-per-channel. WS providers vary widely in multiplexing tolerance. Test signal coverage per channel before trusting a shared connection.
Telethon catchup on startup TODO Signal copier bots missed signals during a 13-hour disconnect because NewMessage doesn't fire for messages received while offline. On bot startup, always backfill from the last seen message ID forward. Still not implemented — add this when next touching the copier bots.

The reel’s useful addition: don’t think of caching as one tool. Think in layers, from closest to the user down to the database:

30-second query triage — don’t upgrade hardware first (IG · 2026-06-13 · reel DXtsSUlD1hC · @kodekloud)

A 30-second four-table query is almost never fixed by moving to a bigger DB instance first. Hardware might turn 30s into 25s; the bad query is still bad. Diagnose before scaling up.

  1. Run EXPLAIN ANALYZE first. Look for sequential scans over large tables, ignored indexes, temp sorts, hash joins over huge row counts, and bad row-count estimates.
  2. Add targeted indexes, not indexes everywhere. Prioritize columns used in WHERE, JOIN ON, and ORDER BY. Use composite indexes matching real filter order; remember every index slows writes.
  3. Find N+1 in application code. 100 parent rows + one query per child set = 101 round trips. Fix with eager loading, joins, batched queries, or DataLoader-style batching.
  4. Fix bad joins and over-fetching. Join on indexed keys, select only needed columns, avoid SELECT * on wide tables, and paginate unbounded lists.
  5. Only then consider capacity. Bigger hardware is valid after the plan is sane and traffic actually needs it.
Audit this project for slow database queries before upgrading infrastructure:

1. Find DB queries with joins, aggregations, ORDER BY, COUNT(*), or unbounded list endpoints.
2. For each query, report whether the WHERE / JOIN / ORDER BY columns have appropriate indexes.
3. Look for N+1 patterns in application code: loops that trigger per-row queries, lazy-loaded relations, or repeated fetches.
4. Flag SELECT * on wide tables and endpoints without pagination.
5. For each issue output: file:line | suspected cost | EXPLAIN/ANALYZE command to run | index/app-layer fix | risk of over-indexing.

Do not scale the DB or add indexes blindly. Produce the diagnosis first.

Cache stampede / thundering herd — when expiration goes wrong (IG · 2026-05-30 · reel DYANfXqCYO0)

The problem: a popular cache entry expires. The next 10,000 requests all see "miss" simultaneously, all hit the database to rebuild it, and the DB dies under the spike. "Cache stampede" or "thundering herd."

This is a real failure mode the moment you have any caching layer with non-trivial traffic. Most engineers know only one fix; here are the four, in order of when to reach for each:

StrategyHow it worksWhen to useTradeoff
1. Request coalescing start here Multiple in-flight duplicate requests are folded into ONE upstream call; everyone gets the same result. CloudFlare CDN does this automatically. Default starting point. Easy to implement at CDN layer (Cloudflare) or app layer (most caching libraries). Almost none. Requires the cache layer to support it. Most do.
2. Cache locking First request acquires a lock, rebuilds the cache, others wait in line. You already have Redis. Workload is mostly-reads, can tolerate small wait. If rebuild is slow or fails, thousands of waiters time out. Lock release on failure is tricky.
3. Probabilistic early refresh As cache age approaches TTL, each request has a small but growing chance of triggering background refresh. At min 50 of 60-min TTL, 1% refresh. At min 59, 20%. Refresh spreads naturally. Unpredictable traffic spikes. You don’t know what's hot ahead of time. Backend can handle moderate increased load. More complex implementation. Requires randomized check on every read.
4. Background refresh worker Dedicated worker proactively recomputes hot keys before they expire. Cache never expires from the user’s perspective. You KNOW what's hot ahead of time. Ticketmaster event pages, homepage of a high-traffic site, dashboards. You need a list of "hot keys." Useless for random spikes. Adds infrastructure (worker process).

The right combination

  • Always-on baseline: request coalescing (Cloudflare does it free; @upstash/redis has it; Redis has SETNX-based patterns). No TTL changes needed.
  • Add for unpredictable spikes: probabilistic early refresh — implement in the cache wrapper function.
  • Only when you know the hot keys: background refresh worker (e.g. a cron that pre-warms the homepage cache every 30 sec).
  • Cache locking: only as fallback when nothing else fits. The other 3 are usually better.

Probabilistic early-refresh pseudo-code (the "XFetch" pattern)

async function getCached(key, fetchFn, ttl_seconds, beta = 1.0) {
  const cached = await redis.get(key);
  if (!cached) {
    // True miss — fetch normally
    const fresh = await fetchFn();
    await redis.setex(key, ttl_seconds, JSON.stringify(fresh));
    return fresh;
  }
  const { value, expires_at, compute_time_ms } = JSON.parse(cached);
  const now = Date.now();
  // XFetch: probabilistic early refresh as TTL approaches
  const delta = (compute_time_ms / 1000) * beta * Math.log(Math.random());
  if (now - delta * 1000 >= expires_at) {
    // Background refresh — don’t block the user
    void (async () => {
      const fresh = await fetchFn();
      await redis.setex(key, ttl_seconds, JSON.stringify({
        value: fresh,
        expires_at: Date.now() + ttl_seconds * 1000,
        compute_time_ms: Date.now() - now,
      }));
    })();
  }
  return value;
}

The math: delta grows toward zero as TTL approaches. When now - delta >= expires_at becomes true, the entry is "due" for refresh. The randomness means different requests will trigger at different moments, spreading the refresh load.

Relevance for Asi: the bots’ orderbook caches, the client dashboards that show "live" data — anywhere you cache something expensive AND have multiple concurrent users. Most apps below 100 concurrent users don't see this problem; above that it bites. Worth knowing the 4 patterns before you need them.

Debouncing — the 5-second performance fix every search/filter needs (IG · 2026-05-30 · reel DY79qxIvkku)

The reel framed it as "the 5-second fix for vibe-coded apps". The pattern AI tools default to: a search input that fires a DB query on every keystroke. User types "hello" → 5 DB queries. Type fast → API is hammered, results flicker, autocomplete is laggy.

The fix: debounce. Wait until the user stops typing for N milliseconds, then fire one query.

The minimum-viable debounce (React + TanStack Query)

import { useState, useEffect } from "react";
import { useQuery } from "@tanstack/react-query";

function useDebouncedValue(value, delay = 300) {
  const [debounced, setDebounced] = useState(value);
  useEffect(() => {
    const t = setTimeout(() => setDebounced(value), delay);
    return () => clearTimeout(t);
  }, [value, delay]);
  return debounced;
}

function SearchBox() {
  const [query, setQuery] = useState("");
  const debouncedQuery = useDebouncedValue(query, 300);  // wait 300ms after stop

  const { data, isLoading } = useQuery({
    queryKey: ["search", debouncedQuery],
    queryFn: () => fetch(`/api/search?q=${debouncedQuery}`).then(r => r.json()),
    enabled: debouncedQuery.length >= 2,  // don’t query on 0-1 chars
  });

  return (
    <>
      <input value={query} onChange={e => setQuery(e.target.value)} />
      {isLoading ? <Spinner /> : <Results data={data} />}
    </>
  );
}

The 3 timing values you actually need to know

DelayUse caseWhy
150–200 msTypeahead autocomplete (Algolia-style instant search)Fast enough to feel real-time. Below 150ms users will trigger ~3 fetches per word.
300 ms ⭐Default for search boxesSweet spot. Average user pauses ~400ms between words; 300ms catches the pause.
500–800 msHeavy / expensive query (server-side full-text search, LLM-backed)Give the user time to finish thinking. Show "type more to search…" hint while waiting.

Related patterns

  • Throttle (vs debounce) — fires at most once per N ms during a stream of events. Use for: scroll handlers, resize, mouse-move. Not for search input (use debounce).
  • Cancel in-flight fetches — when a new debounced query starts, abort the previous request. TanStack Query handles this automatically; for raw fetch use AbortController.
  • Show loading state during typing — even while debouncing, show a small spinner so the user knows the system is responsive (Section 9.4 inline spinner pattern).

Libraries (if you don’t want to write your own): use-debounce on npm (small, just hooks), lodash.debounce (classic but heavy if you don’t already have lodash), or write the 8-line hook above and skip the dependency.

15. File storage architecture (S3 pre-signed URLs, never proxy files)

Source: IG reel DYk0S1pppMl (2026-05-30) — Google Drive file upload service design interview. Same 4-version progression structure as Sections 6 (Payments) and 7 (Feed): naive → incremental fix → "ah-ha, that’s how it should be done." Belongs in Part III (Architecture Playbooks) conceptually even though it ended up at the end of the file.

When this section applies: any client project with file uploads — profile pictures, documents, PDFs, audio, video. Examples from Asi’s portfolio: a clinic that uploads patient X-rays, a marketplace where sellers upload product images, a course platform where instructors upload videos.

15.1 Version 1 — naive: files in Postgres

The default AI suggestion when you say "I need file uploads":

  1. User POSTs file + metadata to your API.
  2. API stores the file BLOB in Postgres + metadata row.
  3. API returns success.

Why this breaks:

  • Postgres is bad at large blobs. 50MB rows kill query performance.
  • Backup size explodes. A 100GB DB of files takes forever to back up / restore.
  • You pay for hot DB storage for files that get touched once a year.

15.2 Version 2 — metadata in Postgres, file in S3 (via your server)

Move files to object storage, keep metadata where it’s queryable:

  1. User POSTs file + metadata to your API.
  2. API stores file in S3 (or R2 / GCS / Supabase Storage).
  3. API writes the S3 key + metadata row in Postgres.
  4. API returns success.

Better — but still has a real problem: every file goes through your server. A 500MB upload occupies your server’s RAM and bandwidth and request timeout. On Vercel serverless functions you have a 4.5MB request body limit by default; uploads of larger files fail.

15.3 Version 3 — pre-signed URLs (the right architecture)

Files never touch your server. Your server only mints a temporary signed URL that authorizes the user to upload directly to S3.

Upload flow

  1. User says "I want to upload logo.png (2MB, image/png)".
  2. Your API:
    • Checks auth: this user is allowed to upload.
    • Generates a pre-signed PUT URL for an S3 key like uploads/{user_id}/{uuid}.png. Expires in 15 minutes.
    • Writes a "pending upload" row in Postgres (or skips this until the upload completes — see post-upload webhook below).
    • Returns the URL to the client.
  3. Client uploads the file directly to S3 via PUT to that URL. Your server never sees the bytes.
  4. Client confirms to your API: "upload done at key X". Your API verifies the object exists in S3, writes the final metadata row.

Download flow (same pattern)

  1. User requests file ID.
  2. Your API checks auth, looks up the S3 key, generates a pre-signed GET URL (expires in 15 min).
  3. Returns URL to client.
  4. Client downloads directly from S3.

Why this matters at scale (additional context — reel DYPp-arDNmJ, 2026-05-30)

A second reel on the same topic surfaced this framing — useful for explaining the decision to clients:

  • Thread starvation: a 2GB upload through your server holds a request thread (and the memory) for the entire transfer. At 100 concurrent uploads of 2GB each, the API is doing zero application work — just moving bytes.
  • Double bandwidth bill: client → your server → S3. You pay egress on the second hop. Pre-signed URL = client → S3 directly. One transfer, one bill.
  • Vercel hard limits: Vercel serverless function body is 4.5MB by default. Anything bigger fails outright. Pre-signed URLs bypass the limit entirely.
  • Server returns to its real job: from "handling gigabytes of binary" to "handling a few hundred bytes of JSON" — exactly what application servers are good at.

The S3 completion event — kick off downstream work

When the client finishes uploading directly to S3, you usually need to do something next: generate thumbnails, transcode video, run virus scan, update a database row, send a notification. S3 fires an event when the upload completes — use it instead of trusting the client to call you back:

# S3 → SNS / SQS / Lambda on PutObject
# (set up in the bucket’s Event Notifications)

# Lambda example (Node.js):
export const handler = async (event) => {
  for (const record of event.Records) {
    const bucket = record.s3.bucket.name;
    const key = decodeURIComponent(record.s3.object.key.replace(/\+/g, " "));
    const size = record.s3.object.size;

    // 1. Verify size + key match the user’s pending upload row in your DB
    // 2. Run virus scan / transcoding / thumbnail generation
    // 3. Update DB: status = "ready"
    // 4. Notify user via webhook / push notification
  }
};

Why event-driven, not "trust the client": a malicious or buggy client might never call back, or might call back with a false key. The S3 event is the only source of truth that "this file actually exists in this bucket."

15.4 Pre-signed POST vs PUT — pick the right one

Pre-signed PUT URLPre-signed POST request (form)
Simple. One URL = one operation on one key. More complex: a JSON policy with rules.
Client can upload anything to that key — your only control is the key name and content-type if you encoded it. Server-side enforcement of: max file size, allowed content-types, key prefix, custom metadata.
Right for trusted clients, simple uploads, when you control the client app. Right for browser uploads from untrusted clients. The policy stops users from uploading 50GB or executable files.

15.5 Large files — multipart upload

  • Pre-signed URLs cap at 5GB per single upload.
  • For larger files (up to 5TB), use S3 multipart upload: split the file into 5MB–5GB parts, get a pre-signed URL for each part, upload in parallel, then call a "complete multipart upload" endpoint that stitches them.
  • Max 10,000 parts. Most apps will never need this — but if you’re building a backup tool, a video platform, or anything with 5GB+ assets, plan for it from day one.

15.6 Expiration times

Use caseRecommended TTL
Upload URL15 minutes (default). Users start uploading immediately.
Download URL (private file)15 min to 1 hour. Long enough to download, short enough that a leaked URL is mostly useless.
Public asset (profile picture in HTML)1–24 hours. Or use CloudFront / Cloudflare CDN in front of S3 with cached responses — no pre-signed URL needed.
Background data export user requested24 hours. They might not download immediately.

Max TTL: 12 hours via the AWS console, 7 days via SDK/CLI.

15.7 Security checklist for file uploads

[ ] Authentication required to get a pre-signed URL (auth check in API)
[ ] Authorization check: this user can upload to this path
    (e.g. only to /uploads/{their_user_id}/, never to /uploads/{someone_else}/)
[ ] Pre-signed POST with content-length-range condition for browser uploads
    (prevents 50GB uploads from a malicious client)
[ ] Pre-signed POST with content-type allowlist for browser uploads
    (prevents .exe being uploaded with image extension trick)
[ ] Server-side virus / malware scan if accepting executable types
    (ClamAV in a Lambda triggered on PUT, or use a service like VirusTotal API)
[ ] S3 bucket is NOT public — pre-signed URLs are the only read path
[ ] CORS configured on the bucket to only allow your app’s origins for browser uploads
[ ] CloudTrail logging enabled on the bucket so you can audit who uploaded what
[ ] Lifecycle rules: move old uploads to S3 Glacier after N days for cost
[ ] Backup: bucket versioning enabled (so accidental delete doesn’t lose data)
[ ] For Supabase users: Supabase Storage uses the same pre-signed URL pattern
    under the hood. Same principles apply, same checklist.

15.8 Audit prompt for existing file-upload code

This project has a file upload feature. Audit it against the 4-version progression:

V1 (files in Postgres): grep for `bytea`, `blob`, large columns being inserted.
   If found → CRITICAL, migrate to S3.
V2 (files through server): find the upload route handler. Does it
   `await req.formData()` or similar and then upload to S3? If yes,
   server is in the path → severity HIGH.
V3 (pre-signed URLs): is there a route that generates a pre-signed URL and
   returns it to the client? If yes, are these checks present:
   - Auth required on the URL-mint route?
   - Authorization: user can only mint URLs for paths they own?
   - Pre-signed POST with content-length-range + content-type allowlist?
   - URL TTL ≤ 1 hour?
   - S3 bucket itself not publicly readable?

For each gap, output: { version, file:line, severity, fix recommendation }.

Cross-reference: if the project uses Supabase Storage, treat that as already-V3
(it’s pre-signed URLs under the hood) but check the same Auth/Authz/TTL items.

Don’t change code. Just the audit.

15.9 CDN delivery + metadata-only DB rows

Source: IG reel DZxfOW9xsFD (2026-06-20, @mattmurphyai). This reel is mostly a simpler restatement of the existing Section 15 rule, but it adds a useful client-delivery framing: the database stores metadata and a pointer; object storage stores bytes; the CDN serves public bytes.

LayerOwnsShould not do
DatabaseFile metadata: owner, object key/URL, MIME type, size, status, timestamps, permissionsStore image/PDF/video bytes in bytea/blob columns
Object storageActual file bytes: S3/R2/GCS/Supabase Storage bucket objectsAct as the authorization source of truth
CDNFast delivery for public or safely-cacheable assets: profile pictures, product images, static downloadsCache private/user-specific files without a correct cache key or signed URL policy
Rule of thumb: profile pictures and public product images should usually be served through CloudFront / Cloudflare / Vercel Image Optimization / Supabase CDN. Private documents should stay behind signed URLs and short TTLs. Never let the convenience of a CDN bypass the auth model.

Audit additions

  • Search for DB columns named image, file, avatar, pdf, blob, bytea. Confirm they store a URL/key, not bytes.
  • For public images, verify there is a CDN/image-optimization path. A profile picture request should not hit the app server on every page load.
  • For private files, verify the DB row stores the object key and permission model, then the API mints short-lived signed GET URLs after authorization.

17. Working with AI coding agents — the 7 Karpathy habits

Source: X article by @scottybeamio (2026-05-28, 240K views) summarizing Andrej Karpathy’s system for working with AI coding agents. Karpathy: OpenAI co-founder, ex-head of AI at Tesla, Stanford. The article’s thesis hits hard: the gap between people who get great output from AI and people who don’t is not prompt skill — it’s the infrastructure around the prompt.

Why this belongs here, at the end: this section is meta — it’s about how Asi uses Claude Code itself, not what to build with it. Belongs to Part VIII (Operational Knowledge) alongside Section 12 (bot patterns) and Section 13 (reusable prompts). Placed at the end because it was added late, but read it before anything else: it changes how you read the rest of the doc.

17.1 The 7 habits (full breakdown)

Habit 1 — Stop tweaking prompts. Add context.

The "prompt engineering guru" industry says: learn the right magic incantation and the model obeys. Karpathy: this is wrong. The reason people iterate 100 times and still get bad output is missing context, not bad wording.

The formula:

  • Write a standard, clear request — no "act as an expert" theatrics.
  • Always include a concrete example of what good output looks like.
  • Paste the full error message or full background — never a trimmed snippet. "I cut it to save context window" → the model fills the gap by guessing → guesses wrong → you blame the model.
  • When the model can’t see something, it confabulates. Don’t make it confabulate.

Habit 2 — Your CLAUDE.md is probably garbage. Fix it.

If you copied it from someone else’s template or let Claude write it for itself, it’s not actually working for you. Karpathy’s 5-item requirement for a working CLAUDE.md:

  1. Who you are (background, role, what kind of problems you bring).
  2. What the project is (general frame only — don’t over-specify).
  3. What NOT to touch (files / patterns / paths that are off-limits).
  4. File naming conventions (so generated files don’t look like alien artifacts).
  5. How to format responses (concise? bullets? markdown? Hebrew? code-first?).

If you only use browser AI (Claude.ai, ChatGPT) — same logic. Set a pinned brief / custom instructions covering these 5.

Habit 3 — Build a 3-layer system. Stop restarting from zero.

Karpathy’s actual structure inside any active project:

LayerWhat it isWho writes it
/rawSource material dumped in as-is — API docs, PDFs, screenshots, transcripts, error logsYou (raw dumping, no formatting)
/wikiStructured pages that summarize and connect what’s in /rawThe model (you instruct it to process /raw → /wiki)
CLAUDE.mdStanding operating principles (the 5-item brief from Habit 2)You

New source arrives → drop in /raw → tell the model "process this." Saved time per day: ~30 min, compounding. If your project lives longer than 2 days and you’re re-explaining everything in every new session, you don’t have a workflow — you have a loop.

Habit 4 — After every strong answer, save it permanently.

The default habit kills long-term productivity: get a great response → copy result → close tab → forget. Karpathy’s rule: after every valuable response, tell the model:

"Save this as a permanent page: wiki/topic/.md"

Then periodically audit your wiki for duplicates, conflicts, outdated info. Skip this and your best AI outputs drown in chat history; you’ll spend hours re-solving things you already solved.

Habit 5 — Any project lasting > 1 week needs index.md + log.md.

Two files, two purposes:

FilePurposeFormat
index.mdA map of everything that exists in the projectList of files + 1-line description per file
log.mdRunning changelog of what you did whendate | type | description
e.g. 2026-05-28 | summary | customer interview breakdown

If you vibe-code 1–2 hours a day for 2 weeks, you genuinely won’t remember what you built on day 3. These two files are your memory layer.

Habit 6 — AI is a brilliant intern with no taste. Keep it on a short leash.

Karpathy’s framing: AI agents are "superpowered interns with massive knowledge, who constantly hallucinate and have zero taste for code." The working loop:

  1. Load full context (CLAUDE.md, /wiki, /raw — everything relevant).
  2. Ask for 2–3 options for the next small step only.
  3. Pick one.
  4. Evaluate. Test. Commit.
  5. Repeat from step 2.

Never ask it to do everything in one prompt. That’s how you get 500 lines of undebuggable mess. Smaller commits = recoverable mistakes. Bigger commits = ratcheting toward chaos.

Habit 7 — The 1-sentence HTML trick for research prompts.

Add this to the end of any analysis / research / breakdown prompt:

Structure your final response as a self-contained HTML file.

AI models render anything into clean, navigable HTML in seconds. Reading time drops dramatically. Costs one sentence; benefit is enormous on long analyses.

17.6 The Wiki Layer — deep dive (the part Habit 3 only hinted at)

Source: X article by @bonsaixbt (2026-05-26, 870K views). Standalone deep-dive on the same Wiki Layer concept that Karpathy describes in Habit 3 — but with the concrete tooling and structure that the 7-habits article only hinted at. Read this if you actually want to set up the system.

The framing line that sells it

"Your LLM is burning through tokens — Karpathy found a way to save 90%."

The core insight: every time you ask an LLM about your project, you re-upload the same raw files. The model re-reads them every time. Token waste is enormous; quality drops because the model loses context across sessions. The Wiki Layer fixes this by doing the cleanup + structure ONCE, then operating on the structured version forever after.

What you actually get when you build it

  • 70-90% token savings on repeated queries (no more re-feeding raw PDFs / HTML / spreadsheets).
  • Significantly better answer quality — the model works from cleaned, structured data instead of guessing through formatting noise.
  • Automatic links between documents — wiki-style [[Page_Name]] references.
  • Visual knowledge graph (when paired with Obsidian — see below).
  • System grows + updates itself — every new piece of source material gets cleaned and linked into the existing wiki.
  • Privacy — entirely on your local machine. Nothing in the cloud.

The 3-folder structure (concrete)

FolderWhat goes hereWho maintainsRule
raw/ Original materials: HTML, PDFs, text notes, screenshots, spreadsheets, transcripts, anything. You (just dump files in) Never edit manually. Single source of truth.
wiki/ Clean, structured Markdown files generated by the LLM. Cross-linked with [[Page_Name]] syntax. The LLM (you instruct it to process raw/ → wiki/) The model’s primary workspace from now on.
instructions/ (or templates/) Files defining: how to clean data, which templates to apply, link conventions, metadata fields, update rules. You (write once, refine over time) This is what makes the system reproducible.

Step-by-step: build your first Wiki Layer (≈1 hour setup)

  1. Create the project folder structure: 
    mkdir -p my-project/{raw,wiki,instructions}
cd my-project
# Drop all existing materials into ./raw/
# Examples: client briefs, API docs PDF, screenshots, meeting notes
  2. Write the structuring-agent prompt in instructions/structure.md: 
    You are a knowledge-base structuring agent. Your job is to process files
in raw/ and produce clean, interlinked Markdown in wiki/.

For each file in raw/:
1. Strip technical junk: ads, navigation, headers, footers, formatting noise.
2. Extract: title, date (if findable), key topics (3-5), key entities (people,
   companies, products, technologies).
3. Convert to clean Markdown with consistent headings.
4. Apply the templates in instructions/templates/ based on document type.
5. Cross-link to existing wiki/ pages via [[Page_Name]] syntax.
6. Add YAML frontmatter:
   ---
   source: raw/[original-filename]
   date_processed: YYYY-MM-DD
   topics: [topic1, topic2]
   entities: [entity1, entity2]
   ---
7. Save to wiki/[topic]/[slug].md
8. Update wiki/index.md with a one-line entry.

Conflict rule: if a new file contradicts an existing wiki page, do NOT
overwrite. Create wiki/conflicts/[topic]-[date].md and flag for me to
resolve.
  3. Run the agent: in Claude Code at the project root, say "Process all files in raw/ according to instructions/structure.md." Wait. Review the first few wiki pages it generates; tighten the prompt if needed.
  4. Open in Obsidian: install Obsidian (free), open the project folder as a vault. You instantly get: visual knowledge graph, full-text search, click-through between linked notes. No extra setup.
  5. Switch your workflow: instead of "upload these 12 PDFs and process this question," tell Claude "Work with my Wiki database inside the wiki/ folder." 90% fewer tokens, 5x faster, much higher accuracy.

17.7 Post-feature cleanup pass — ask Claude to delete code (IG reel DZdboxvTqnm · 2026-06-13)

The reel’s useful point is simple: after vibe coding a feature, the most valuable prompt is often not “write more code” — it is “find what you just made unnecessary and remove it.” AI-assisted feature work tends to leave behind unused files, duplicated logic, half-replaced components, and abstractions that technically work but nobody understands anymore.

Why this matters

  • Feature velocity hides entropy: adding a feature in an hour feels productive, but every feature can leave a small mess.
  • AI tools over-create: they often add new helpers/components instead of noticing an existing one can be reused or deleted.
  • Working code is not necessarily maintainable code: duplicated logic and stale branches become future bugs.
  • Cleanup must be a separate pass: if you mix “build feature” and “delete complexity” in one prompt, the model optimizes for shipping the feature and misses the cleanup.

The workflow

  1. Finish the feature first. Run the app/tests enough to know the feature works.
  2. Commit or stash a checkpoint. Cleanup is easier when you can revert only the cleanup pass.
  3. Run a deletion-focused review. Ask for dead code, unused components, duplicate logic, unnecessary wrappers, and over-complicated state.
  4. Apply only low-risk deletions first. Remove unused files/imports/branches before attempting deeper refactors.
  5. Run tests/build again. The cleanup pass is not done until the same verification still passes.
  6. Commit cleanup separately. Feature commit and cleanup commit should be readable independently.

Claude prompt

I just finished implementing a feature. Before adding anything else, audit the current diff for code that should be deleted or simplified.

Focus on:
1. Dead code: unused files, unused exports, unreachable branches, old components replaced by the new feature.
2. Duplicate logic: functions/components/hooks that now do the same thing in two places.
3. Unnecessary complexity: wrappers, abstractions, state variables, effects, or config added “just in case.”
4. Confusing code that technically works but will be hard to maintain.
5. Tests/mocks/fixtures that are now stale or redundant.

For each finding, output:
- file:line
- delete / simplify / keep
- why it is safe
- exact minimal change

Do not add new functionality. Prefer deletion over refactor. Do not edit yet; report first.

Optional one-shot cleanup command after the report

Apply only the SAFE cleanup items from your report:
- remove unused imports/files/branches
- consolidate exact duplicate logic
- do not change behavior
- do not introduce new abstractions

After editing, run the project’s existing typecheck/tests/build and show the real output.

17.8 Understanding + verification gate before prod (IG reel DZf_wAWzBL3 · 2026-06-13)

The reel’s useful warning: Claude can make you ship faster than you understand. The dangerous part is not that the model writes bad code by default; it is that a working feature can trick you into treating understanding as optional. The feature works, the API responds, the UI looks right — but you have not yet checked security, scale, maintainability, regressions, or test coverage.

Rule: every AI-built feature needs a verification gate before production. Do not ask Claude only “does it work?” Ask what could break, leak data, slow down, confuse the next developer, or regress existing behavior.

The 4-question gate

  1. Security: Did you build this in the most secure way? What user data or privileged action could be exposed if one assumption is wrong?
  2. Efficiency: Did you build this in the most efficient way for the expected traffic/data size? Where are the expensive queries, loops, network calls, or re-renders?
  3. Regressions: What existing behavior could this change or break? Which routes/components/API contracts are now at risk?
  4. Tests: What tests do we need before shipping this? Include happy path, permission failures, edge cases, and regression tests around touched behavior.

When to run it

  • After the feature works locally, before merging/deploying.
  • Before the cleanup pass in Section 17.7 if you suspect the feature architecture is shaky.
  • After the cleanup pass if deletion/refactor changed behavior.
  • Always on client projects that touch auth, payments, personal data, file uploads, integrations, or background jobs.

Claude prompt

I just finished an AI-assisted feature. Before we ship, run a verification gate on the current diff. Do not edit yet; report first with file:line evidence.

Answer these four questions:
1. Security — was this built in the most secure way? What user data, auth boundary, secret, admin action, or tenant boundary could be exposed?
2. Efficiency — was this built in the most efficient way for expected traffic/data size? Flag expensive queries, N+1 patterns, unnecessary network calls, heavy client work, and missing indexes/caching.
3. Regressions — what existing behavior could this introduce regressions into? List affected routes/components/API contracts and why.
4. Tests — what tests must exist before shipping? Include happy path, permission failures, edge cases, and regression tests.

18. Webhook delivery architecture (outbox / retries / DLQ / replay)

Source: IG reel DZKq0TiRiij (2026-06-06, @kodekloud). The useful part is not “use webhooks” — it is the production delivery architecture for sending millions of customer webhooks without losing events or letting one slow customer take everyone down.

When this section applies: any product where your system sends events to customer-owned endpoints: order updates, payment events, CRM sync, accounting integrations, marketplace seller events, notifications, or partner APIs. If you promise customers “we will notify your system when X happens,” this is the pattern.

18.1 Version 1 — direct POST from the request handler (don’t)

The naive implementation is: event happens → backend immediately POSTs to the customer URL → continue the user request after the webhook returns.

  • Blocks your own request path: a slow customer endpoint makes your user-facing request slow.
  • Loses events: if the customer endpoint is down and you did not persist the event first, there is nothing reliable to retry.
  • Creates cascading failures: customer outage becomes your outage.

18.2 Version 2 — transactional outbox (durability first)

Write the event to a durable outbox table in the same transaction as the business change, then let separate workers deliver it asynchronously.

BEGIN;
  UPDATE orders SET status = 'paid' WHERE id = $order_id;
  INSERT INTO webhook_outbox (customer_id, event_type, payload, status)
  VALUES ($customer_id, 'order.paid', $payload, 'pending');
COMMIT;

Rule: if the business event committed, the webhook event must be durably recorded too. Delivery is allowed to be late; the event is not allowed to disappear.

18.3 Version 3 — dispatcher + customer isolation

A single global worker pool still has a head-of-line blocking problem: one customer with a slow endpoint can consume every worker. Add a dispatcher that schedules fairly and enforces per-customer concurrency.

ComponentJobProduction rule
OutboxDurable event storePending / delivered / failed / dead-lettered state; unique event IDs.
DispatcherPicks the next deliverable eventSkip customers already at their concurrency limit.
Worker poolPOSTs to customer endpointsShort timeout, bounded concurrency, structured result logging.
Per-customer limitsNoisy-neighbor protectionCustomer A’s outage only slows Customer A.

18.4 Version 4 — smart retries (temporary vs permanent)

Every delivery attempt needs a deadline and a retry classification.

  • Success: 2xx → mark delivered and store response metadata.
  • Temporary failure: timeout, connection error, 429, 5xx → retry with exponential backoff and jitter.
  • Permanent failure: malformed URL, DNS impossible, many 4xx responses → stop retrying unless customer configuration changes.

Use a short default timeout (for example 10 seconds). Do not let a webhook worker hang forever on a customer endpoint.

18.5 Version 5 — dead letter queue + replay UI

After max retries, move the event to a dead letter queue instead of deleting it. The DLQ is the support/debugging surface:

  • support can see exactly which events failed and why;
  • customers can fix their endpoint and request replay;
  • engineering gets an audit trail of every delivery attempt;
  • events are never silently lost.

18.6 Complete architecture

Backend transaction
   ↓ writes business row + webhook_outbox row
Transactional Outbox
   ↓ pending events
Dispatcher
   ↓ fair scheduling + per-customer concurrency limits
Worker Pool
   ↓ signed HTTP POST with timeout
Customer Endpoints
   ↓ success / temporary failure / permanent failure
Retry Scheduler → Dead Letter Queue → Replay UI

18.7 Security and observability checklist

  • Sign every request: HMAC signature using a per-customer secret; include timestamp to prevent replay attacks.
  • Idempotency for receivers: include a stable event ID so customers can dedupe duplicate deliveries.
  • Attempt log: store attempt number, status code, latency, response snippet, next retry time.
  • Dashboards: delivery rate, failure rate, DLQ count, p95/p99 delivery latency, failures by customer.
  • Customer controls: endpoint URL, secret rotation, pause/resume, replay failed events.

19. Mobile deep links (Universal Links / Android App Links / Expo)

Source: IG reel DZLHBM9xY33 (2026-06-06, @mattmurphyai). The reel is useful for future mobile apps: when a user shares a link to app content, the same URL should open the installed app; if the app is not installed, it should open the web page and invite install. Without this, shared links dump users into a browser/login wall and conversion dies.

When this matters for Asi: skip this for normal brochure sites and plain web apps. Use it when a client/project has a real mobile app or Expo/React Native app with shareable content: profiles, orders, events, invoices, bookings, restaurant menus, posts, or any object that users send to each other.

19.1 The failure mode

  • User shares https://example.com/orders/123.
  • Recipient has the app installed, but the link opens Safari/Chrome instead.
  • The web page asks them to log in again or cannot show the mobile-only flow.
  • They bounce — not because the app feature is bad, but because the link-routing contract is missing.

Rule: app links are not “nice to have” once mobile sharing matters. They are part of activation and retention.

19.2 Apple Universal Links

iOS uses a domain-hosted JSON file to prove that your domain is allowed to open your app.

https://example.com/.well-known/apple-app-site-association
  • No .json extension.
  • Serve as JSON, ideally application/json.
  • No redirects — Apple must fetch the file directly.
  • Add the associated domain entitlement in the app: applinks:example.com.
  • Map only the paths that should open the app, not the whole site by accident.
{
  "applinks": {
    "apps": [],
    "details": [
      {
        "appIDs": ["TEAMID.com.company.app"],
        "components": [
          { "/": "/orders/*", "comment": "Open order details in app" },
          { "/": "/events/*", "comment": "Open event details in app" }
        ]
      }
    ]
  }
}

19.3 Android App Links

Android uses Digital Asset Links plus intent filters in the app manifest.

https://example.com/.well-known/assetlinks.json
[
  {
    "relation": ["delegate_permission/common.handle_all_urls"],
    "target": {
      "namespace": "android_app",
      "package_name": "com.company.app",
      "sha256_cert_fingerprints": ["AA:BB:CC:...:FF"]
    }
  }
]

In native Android, add an intent-filter with android:autoVerify="true", https scheme, your host, and the path prefixes you support.

19.4 Expo / React Native setup

Expo can generate most of the native configuration from app.json / app.config.ts and route URLs through Expo Router.

// app.config.ts — sketch, verify exact IDs per project
export default {
  expo: {
    scheme: "myapp",
    ios: {
      bundleIdentifier: "com.company.app",
      associatedDomains: ["applinks:example.com"]
    },
    android: {
      package: "com.company.app",
      intentFilters: [
        {
          action: "VIEW",
          autoVerify: true,
          data: [{ scheme: "https", host: "example.com", pathPrefix: "/orders" }],
          category: ["BROWSABLE", "DEFAULT"]
        }
      ]
    }
  }
}

With Expo Router, keep web and app routes aligned where possible: /orders/[id] on web should correspond to the same logical screen in the app.

19.5 Fallback: app not installed

Do not send users to a dead app-store jump immediately. The URL should still be a real web URL:

  • If app installed → open directly in app.
  • If app not installed → open the web page for that content.
  • On the web page → show the useful content if allowed, plus a smart banner / install CTA.
  • After install/login → preserve the original destination so the user lands on the shared item, not the homepage.

19.6 Verification checklist

[ ] https://domain/.well-known/apple-app-site-association returns 200, no redirect
[ ] https://domain/.well-known/assetlinks.json returns 200, no redirect
[ ] Files contain the correct bundle/package IDs and Android SHA-256 fingerprint
[ ] iOS associated domains include applinks:domain
[ ] Android intent filters include https + host + pathPrefix + autoVerify
[ ] Web fallback page works without the app installed
[ ] After login/install, the original deep-link destination is preserved
[ ] Test on a real iPhone and a real Android device — simulators are not enough
