2. The 30-min security audit runbook

Four steps. Apply to any Next.js / Node.js project before shipping to a client. The whole thing takes about 30 minutes once you know the moves.

Step 1 — Dependency vulnerabilities (npm audit)

Goal: Catch known CVEs in installed packages.

# In the project root:
npm audit --omit=dev          # production deps only
npm audit                     # everything
npm outdated                  # what's old

How to read the output

  • Critical / High Must fix before shipping. Try npm audit fix first; if that fails, manually upgrade the package.
  • Moderate Fix if exploitable in your usage path (look at the CWE description).
  • Low / Informational Can ignore if the vulnerable code path is not reachable.

Common gotchas

  • npm audit fix --force can break the app — run tests after. Prefer manual upgrade for major-version bumps.
  • If lockfile is pnpm-lock.yaml or yarn.lock, use pnpm audit / yarn audit instead.
  • Next.js projects: pay extra attention to next itself, @auth/*, anything that touches server actions.

Step 2 — Auth boundary tests (IDOR — "listed from users")

Goal: Verify that User A cannot read or modify User B's data by tweaking IDs in URLs or API bodies.

This is the single highest-value test because IDOR (Insecure Direct Object Reference) is the most common and most damaging bug in CRUD apps. Having a login page is not the same as having authorization.

Manual test (~10 min per app)

  1. Create two test users: alice@test.com and bob@test.com.
  2. Log in as Alice. Create a resource (a record, an order, a profile, whatever the app owns). Note its ID — e.g., /api/orders/42.
  3. Open Network tab in browser dev tools. Find the API call to fetch order 42. Note its URL.
  4. In another browser / incognito, log in as Bob.
  5. From Bob's session, directly request Alice's resource:
    • URL approach: paste https://app.example.com/orders/42 in Bob's browser.
    • API approach: in Bob's dev console, run fetch('/api/orders/42').then(r => r.json()).then(console.log)
  6. PASS Bob gets 403 Forbidden or 404 Not Found.
    FAIL Bob sees Alice's data.

Automated grep (find suspicious code patterns)

# Find API routes that fetch by ID but don't filter by ownership
grep -rn "findUnique\|findFirst\|findOne" --include="*.ts" --include="*.js" -A 3 . \
  | grep -i "where.*id" \
  | grep -v "userId\|user_id\|ownerId\|owner_id"

Any match that doesn't filter by userId/ownerId is suspicious — it returns the record regardless of who's asking.

Common Next.js / API-route patterns

PatternVerdict
prisma.order.findUnique({ where: { id } })FAIL unless followed by an ownership check.
prisma.order.findUnique({ where: { id, userId: session.user.id } })PASS
Server actions / route handlers that take params.id from the URL and look it up without filtering by sessionFAIL
Don't forget mutation endpoints. Also test:
  • PATCH /api/orders/42 from Bob's session with a body change — does it succeed? If yes, FAIL.
  • DELETE /api/orders/42 from Bob's session — does it succeed? If yes, FAIL.

Fix pattern: every database read/write inside a route should be scoped by the current user's session — never trust an ID from the URL or body on its own.

Step 3 — Secrets hygiene

Goal: No secrets in code, no secrets in front-end bundles, no secrets in Git history.

3a — Is .env tracked by Git?

git ls-files | grep -E "^\.env($|\.)"

Expected output: EMPTY. Any .env file shown is committed and likely exposed.

3b — Were secrets ever committed?

git log -p --all -S "API_KEY" --source -- "*.env*" 2>/dev/null | head -50
git log -p --all -S "SECRET"  --source                2>/dev/null | head -50
git log -p --all -S "sk_live" --source                2>/dev/null | head -30   # Stripe live keys
git log -p --all -S "AKIA"    --source                2>/dev/null | head -30   # AWS access keys

Any output = a secret was once committed. Rotate it today. Removing from git history doesn't help — assume it's already scraped by bots indexing GitHub.

3c — NEXT_PUBLIC_* leaks into the browser?

grep -rn "NEXT_PUBLIC_" --include="*.ts" --include="*.tsx" --include="*.js" --include="*.jsx" . \
  | grep -i -E "SECRET|API_KEY|TOKEN|PASSWORD|PRIVATE"

Anything matching = bug. NEXT_PUBLIC_* gets bundled into the browser. Move to server-only.

3d — Hardcoded secrets in code?

grep -rEn "(sk_live_|sk_test_|AKIA[A-Z0-9]{16}|ghp_[A-Za-z0-9]{36})" \
  --include="*.ts" --include="*.tsx" --include="*.js" --include="*.json" .

Should return nothing. Matches indicate Stripe live, Stripe test, AWS access, GitHub PAT respectively.

Fix pattern

  • Anything in .env should be server-side only.
  • For Next.js, only prefix with NEXT_PUBLIC_ if it's something safe to ship to a browser (e.g., a public Supabase anon key, an analytics ID). Service-role keys / private API keys → never.
  • If a secret was ever committed → rotate it today.

Cloak Browser unverified

What: Custom Chromium build with 16 patches compiled into the source itself (not runtime patches like Playwright-stealth). Drop-in replacement for Playwright.

Why interesting: Reportedly passes reCAPTCHA v3 with score 0.9 (human-equivalent), Cloudflare Turnstile, fingerprint.js, 14/14 browserscan stealth tests. Could re-open scraping for venues that block your REST API (Bitunix 403, Binance 418-ban).

How to find: GitHub search for "Cloak Browser".

Before installing:

  1. Read the README and the patch list under patches/ to make sure nothing exotic is happening to your system.
  2. Look at star count, age, and contributors. If it's brand new with no track record, treat any binary download with caution — prefer building from source.
  3. Run it inside a Docker container or a VM the first few times to limit blast radius.

Verdict: Worth a 30-min exploration. Useful if/when you want to retry scraping Bitunix L2 depth or Binance candles after an IP/API ban. Don't put it in the live-trading critical path until you've stress-tested it for at least a week.

ScrapeGraphAI strong evaluate

Open-source Python scraping library that uses an LLM + graph logic instead of CSS selectors. From IG reel DYrlQReEbxS (2026-05-25). The reel framed it as "every paid scraping company just got destroyed by one free GitHub repo" — typical hype, but the underlying project is real and serious.

What it does:

  • Give it a URL + a plain-English description of what data you want. It infers structure from the page and returns it.
  • LLM-agnostic — OpenAI, Azure OpenAI, Gemini, Groq, or local models via Ollama.
  • Supports websites + local documents (XML, HTML, JSON, Markdown).
  • Resilient to layout drift — when a site changes its markup, your prompt usually still works (selector-based scrapers break).
  • License: MIT — fully commercial-usable.

Why this is relevant for Asi specifically:

  • Bitunix 403 / Binance 418-ban scenarios — when REST APIs are blocked, you can scrape the web UI instead. ScrapeGraphAI + Ollama (local LLM, no API cost) means you can scrape order books or funding rates without paying for API access or for an LLM service per request.
  • For client projects — competitor monitoring, price tracking, lead enrichment. The reel's "$5,000 per scraping project" framing is real — agencies do charge that. A one-afternoon setup for a Bashier-style B2B client can be a real upsell.
  • Stack pairing with Cloak Browser (Section 3.3 above): Cloak Browser handles bot-detection bypass; ScrapeGraphAI handles structured extraction. Together they cover the full "scrape any site, get clean data" pipeline.

Repo: github.com/ScrapeGraphAI/Scrapegraph-ai · PyPI: pip install scrapegraphai · LangChain integration: langchain-scrapegraph · Tutorial: practical walkthrough.

Before treating it as production:

  1. The reel mentioned "23,000 stars and an Italian developer." Star count is a vanity metric — verify the repo has recent commits and responsive issue triage before betting on it for a client deliverable.
  2. LLM-based scraping is expensive at scale if you use a paid model. Default to local Ollama for high-volume work; pay per-call only when you need quality the local can't give.
  3. For legally sensitive scraping (anything behind login, anything paywalled, anything competitor-targeted): respect the target site's ToS and Israeli/EU law. The tool removes the technical barrier but not the legal one.

Use when: you have a Python script that calls an LLM and you want to harden it.

6. Bot code-quality patterns we've learned

Real bugs and fixes we've shipped in the trading bots. Not security per se, but pattern-spotting that transfers to client projects too. Each is worth checking against new code.

PatternWhat we fixedLesson for next time
Exchange-timestamp vs monotonic-time OrderFlowEngine was using time.monotonic() for trade timing, causing live ≠ paper signal divergence. Replaced with exchange-supplied trade timestamps. For anything time-sensitive that needs to match a replay or another engine, use the canonical timestamp from the source — never local clock.
Equity measurement Bot performance was measured by cycle count and total_profit accumulator. Wrong — partial fills inflate it. Switched to equity_end - equity_start. For any performance metric, measure the bottom-line state change, not an event counter.
Frozen-pot equity bug compute_total_equity() dropped pending-LIMIT capital because margin or frozen short-circuited. Fixed: sum both fields. Python's or is value-short-circuit, not None-coalesce. Use x if x is not None else y when both might be zero.
Drift-aware staleness Stale-buy detection compared price to bid instead of bid - N*tick, so every BUY was canceled every 3 min → lost queue position. Added drift threshold + longer timeout. If you cancel-and-replace orders, you lose your queue position. Make staleness rules tolerant unless price has actually moved meaningfully.
Trail-state interference with reset Trail logic re-fired infinitely and interfered with stuck-SELL recovery. Fixed with single-fire flag + gated on not awaiting_reset_exit_fill + cleared in _record_sell_reset. State-machine flags need explicit reset paths. Don't trust other state to clear yours.
WS connection split per channel (Bitunix) Single WS connection for multiple channels silently dropped order-flow signals on big-cap coins. Required 1-connection-per-channel. WS providers vary widely in multiplexing tolerance. Test signal coverage per channel before trusting a shared connection.
Telethon catchup on startup TODO Signal copier bots missed signals during a 13-hour disconnect because NewMessage doesn't fire for messages received while offline. On bot startup, always backfill from the last seen message ID forward. Still not implemented — add this when next touching the copier bots.

7. OWASP-grounded API security claims (fact-checked)

From the @jordan_kodes Instagram reel on 2026-05-02 (DXz5iIwxiuF). Saved at ~/asibrain/links/2026-05-02-api-security-3-things.md.

Claim 1: "Open endpoints — if code doesn't check who's making requests, anybody can hit your data"

TRUE

  • OWASP API Security Top 10 (2023): API1 BOLA (Broken Object Level Authorization) + API2 Broken Authentication.
  • Important nuance: authn ≠ authz. An endpoint can require login and still let user A read user B's data.
  • Mitigation: every object-level read must check current_user.id == resource.owner_id (or via a role/permission system).

Claim 2: "No pagination = DB dump"

TRUE BUT MISLEADING

  • Pagination alone is not a security control. Without rate-limiting, an attacker just loops ?page=1...N.
  • Real mitigations: (a) per-user data filtering on every list endpoint, (b) rate-limiting per IP / user / API key, (c) hard page-size cap (clamp ?limit=10000 to 100), (d) authorization on every row returned.
  • Pagination is fundamentally a performance / UX feature. The closest OWASP mapping is API4 Unrestricted Resource Consumption.

Claim 3: "Excessive error messages tell attackers how your system works"

TRUE

  • OWASP Web Top 10 (2021): A05 Security Misconfiguration; OWASP API Top 10: API8.
  • Raw stack traces leak: database engine + version, ORM + framework versions (CVE matching), file paths, library versions.
  • Mitigation: production returns a generic 500 Internal Server Error + a request ID. Full trace goes to your logging system only (never to the client).

8.1 Emil Kowalski's motion skill

What it does: Adds real motion with proper easing to UI code. Distilled from Emil Kowalski's Animations on the Web course and his open-source projects (Sonner toast library, vaul drawer, etc.). The skill reviews UI code and gives before/after tables, catching common animation mistakes.

What it enforces:

  • UI animations under 300ms (longer = feels sluggish).
  • Custom easing curves instead of CSS defaults (ease, ease-in-out — they look "vibe-coded").
  • Performance optimizations (transforms over layout properties, will-change hints).
  • Accessibility: every animation respects prefers-reduced-motion.

Where to get it (multiple options):

9. Legal compliance for shipped apps

If a project collects any user data — even just an email signup — it needs a privacy policy, terms of service, and a CCPA/GDPR-compliant deletion path. Source: IG reel DYrvI-fAPC2 (2026-05-25). The reel's framing was sharp: "one complaint away from a lawsuit". This isn't paranoia — it's the actual legal floor for any consumer-facing app in 2026.

Relevance for Asi: every Next.js client delivery that has a contact form, signup, account, order, or analytics tracker triggers this. Bake the checklist into pre-delivery for any of: Bashier, gan-tair, hanna-engteacher, faran, eishoron, shwartz, YL-SPORT, code7, hanadavid, hadlut, etc. The cost is one afternoon; the upside is the client never gets a takedown notice.

9.1 The 3-step checklist (~1 afternoon total)

Step 1 — Privacy policy required

Goal: document what data is collected, how it's stored, and how users can delete it. Must cover at minimum: data categories, storage location, retention period, third-party sharing, cookies, user rights, and contact for inquiries.

Free generators (10 min each):

  • Termly — generator + auto-update when laws change. Free tier sufficient for most client sites.
  • PrivacyPolicies.com — alternative generator. Slightly more lawyer-flavored output.
  • Iubenda — more polished, paid for serious products; free tier exists.

Where to put it: linked from the footer of every page, plus on the signup form right next to "I agree."

Step 2 — Terms of Service (ToS) required

Goal: liability limitation + user-conduct rules + dispute resolution + jurisdiction. This is the legal shield. Without it, every user interaction is unlimited liability exposure.

What it must cover:

  • Limitation of liability — caps the maximum legal damages the user can claim (usually limited to fees paid or a small fixed amount).
  • User conduct rules — what users can / can't do on the platform.
  • Dispute resolution — arbitration clause, governing law, jurisdiction (for an Israeli business: usually Israeli law + Israeli courts, unless the client is targeting EU/US).
  • Intellectual property — who owns user-generated content.
  • Termination — when/why you can suspend an account.
  • Modifications — how ToS changes are communicated.

Templates:

  • Termly ToS generator — free, generated in 10 min.
  • PrivacyPolicies sample ToS template — adapt and trim.
  • If the project handles payments or has Israeli-specific obligations (consumer protection law, etc.) — get a real lawyer to review before launch. Costs ~₪500–1500 for a basic SaaS review; cheap insurance.

Step 3 — CCPA + GDPR basics required if any EU/CA users

If the site collects any data from California or EU residents — and any consumer-facing site does, even if accidentally — these two laws apply:

RequirementWhat it meansImplementation
Opt-out Users must be able to say "don't sell my data" / "don't share with third parties" A cookie banner with "Reject all" button. Don't use the dark-pattern "Accept all (highlighted) vs Manage preferences (greyed)."
Data deletion on request User asks → you delete (within 30 days under CCPA, 1 month under GDPR) Add a "Delete my data" button in the account settings or a contact form. It's the law, not a nice-to-have.
Data export User can request a copy of all their data (GDPR Article 15 — right of access) Either auto-generated download in account settings, or manual export within 30 days of request.
Consent for tracking Before any non-essential cookies or trackers (Google Analytics, Meta Pixel, etc.) fire Cookie banner must require explicit opt-in BEFORE the tracker loads. Don't load GA on first visit; only after consent.

9.2 Pre-delivery legal checklist (copy into project)

[ ] Privacy policy generated (Termly / PrivacyPolicies / Iubenda)
[ ] Privacy policy linked from footer + signup form
[ ] Terms of Service drafted and reviewed (lawyer if any non-trivial liability)
[ ] ToS accepted at signup (checkbox, not pre-checked)
[ ] Cookie banner with explicit opt-in (not just "by using this site you agree")
[ ] Cookie banner blocks non-essential trackers (GA, Pixel, etc.) until consent
[ ] "Delete my data" path exists — button in account settings OR a documented email process
[ ] Data export path exists — auto-download OR manual within 30 days
[ ] If using analytics: GA4 anonymized IPs (`anonymize_ip: true`); no PII in event parameters
[ ] If using payments: Stripe / PayPal handles PCI compliance (don't store card data yourself)
[ ] Contact email for data-rights requests (publish in privacy policy)
[ ] Data Processing Agreement (DPA) with vendors that touch user data (Supabase / Vercel / Mailgun / etc. — most have a self-serve DPA in their console)

9.3 Israel-specific notes

  • Privacy Protection Law (חוק הגנת הפרטיות) — Israeli equivalent of GDPR. Requires registration of databases with the Privacy Protection Authority above certain thresholds. Most small client projects don't trigger it, but check if the project handles sensitive categories (health, finance, biometric).
  • Consumer Protection Law (חוק הגנת הצרכן) — for any project with sales, returns, or subscriptions. Mandatory cooling-off period (14 days for online sales), clear pricing display.
  • Israeli email law (חוק הספאם) — explicit double-opt-in required for marketing emails. Pre-checked boxes are illegal. Include "unsubscribe" link in every email.
  • For B2B clients (most of Asi's freelance work): the client carries the obligation, but you carry reputation risk. Spending an afternoon getting the legal footer right is part of the deliverable.
What this section is NOT: legal advice. Generators give you 80% coverage for free; the last 20% (anything custom about your client's product, anything cross-border, anything that touches financial data or minors) needs a real lawyer. Treat this section as "default to compliant" — when the project is anything more than a basic informational site, get human legal review.
